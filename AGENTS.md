# AGENTS.md — Проект озеленения территории

## Границы рабочего пространства (жёстко)

- Рабочая папка проекта — только:
  `D:\Загрузки\Проекты\Проект озеленения территории`
- Это отдельный, самостоятельный проект, разрабатываемый как заявка на хакатон. Никакие другие личные проекты пользователя **не упоминаются по имени нигде в документации и коде этого репозитория** — ни в README, ни в комментариях, ни в служебных строках (User-Agent и т.п.). При необходимости сослаться на ранее наработанный паттерн — только нейтральной формулировкой, без названия исходного проекта или пути к нему.
- Внешние личные проекты пользователя, если к ним нужно обратиться за готовым кодом/паттерном: разрешено только читать и копировать; запрещено писать, редактировать, удалять что-либо внутри них — ни при каких условиях, без явного отдельного разрешения на конкретное действие.
- Ранее заимствованные вспомогательные наработки уже перенесены в `docs/reference_snippets/` — это черновой материал для переписывания под домен DXF/озеленения, не рабочий код проекта. Дальнейшее копирование извне в рамках этого проекта не производится без нового явного запроса, и в этом случае тоже без упоминания источника в документации.

## Целевая среда исполнения

- Продукт по ТЗ ДПиООС должен работать на **MosTex.OS** (Linux, близко к Ubuntu). Windows — не целевая ОС для контура заказчика.
- Разработка допустима на Windows, но код обязан оставаться кросс-платформенным: без Windows-only библиотек/путей, финальная проверка — в Docker-контейнере на Linux.
- Обязательна упаковка в Docker (Dockerfile/docker-compose) — фиксируется как обязательный, не опциональный шаг перед сдачей.

## Не изобретать нормативные пункты

- Любая ссылка на конкретный пункт СП/постановления/МГСН в объяснении посадки должна быть сверена с первоисточником и занесена в `docs/NORMATIVE_REFERENCES.md` со статусом `verified`.
- Пока пункт не сверен — статус `[требует верификации]` и в отчёте пользователю это должно быть видно явно, а не выдаваться за подтверждённую норму.
- Это прямое требование заказчика в ТЗ (интерпретируемость — обязательный критерий оценки) и общее правило работы с юридическими/нормативными данными в проектах пользователя — см. `docs/OPEN_QUESTIONS.md` по недостающим источникам.

## DXF: неприкосновенность исходных слоёв

- Любая операция записи в DXF обязана оставить исходные слои (подоснова, коммуникации, городская среда) геометрически идентичными входному файлу.
- Результат пишется только в новые, явно поименованные слои (`PLANTING_PROPOSED`, `GREEN_AI` и т.п.).
- Перед тем как считать DXF-экспорт готовым — обязателен автоматический diff исходных слоёв вход/выход (см. Layer-Integrity Auditor в `docs/AGENTS_PLAN.md`), а не визуальная проверка на глаз.

## Верификация — не опция

- Ни один сгенерированный план посадки не считается финальным результатом до прохождения всех проверок из `docs/AGENTS_PLAN.md` (норм-комплаенс, целостность слоёв, консистентность ссылок на нормы, регрессия на эталонных данных при наличии).
- Генератор плана и верификатор плана — разный код, верификатор не должен переиспользовать внутренние допущения генератора (иначе он не ловит его же ошибки).

## Логирование

- Значимые решения по архитектуре, найденные баги и добавленные возможности фиксируются в:
  - `docs/BUGS.md`
  - `docs/FEATURES.md`
  - `docs/SESSION_LOG.md`
- Запись делается по ходу работы, не откладывается на конец сессии.

## Порядок работы с задачей

- Одна активная задача за раз (см. `docs/CHECKLIST.md`), не распыляться на несколько направлений одновременно.
- Перед тем как объявить шаг чек-листа выполненным — реальная проверка (прогон, сравнение с эталоном), а не предположение, что код должен работать.
- Новые входные файлы от пользователя (нормативные акты, каталоги посадок, примеры DXF) сначала изучаются и кладутся в `data/raw/` или `docs/tz_source/`, затем результат изучения фиксируется в соответствующем документе (`NORMATIVE_REFERENCES.md`, `DATA_ALGORITHM.md` и т.д.) — не держать выводы только в чате.
