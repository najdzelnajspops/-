# Проект озеленения территории

Сервис для автоматического проектирования озеленения города с учётом расположения подземных коммуникаций и городской среды.

Основа проекта — техническое задание кейса ДПиООС города Москвы (см. `docs/tz_source/03_dpioos_tz.pdf` и его выжимку `docs/TASK_BRIEF.md`). Проект реализует полноценный пайплайн по ТЗ (Service A, см. `docs/ARCHITECTURE.md`): принимает подготовленный проектный слой (геооснова DWG/DXF + инженерные коммуникации + кадастр) и генерирует план посадок с экспортом обратно в DXF.

(Изначально архитектура предусматривала второй, вспомогательный сервис «разовых рекомендаций» по PDF/Excel/DOCX без полноценной геоосновы — не требовался по ТЗ, реализован не был и по решению пользователя (2026-09-24) окончательно исключён из объёма проекта, см. `docs/OPEN_QUESTIONS.md`.)

Проект опирается на реальный датасет хакатона (20 объектов, «Пилотный проект 20 улиц») — структура и выводы из его изучения зафиксированы в `docs/DATA_STRUCTURE.md`.

## Как запустить

**CLI (основной способ по ТЗ)**:
```
python -m pipeline.run --input <DXF...> --base-dxf <DXF> --territory-category dvorovye --output-dxf out.dxf --output-report out.json
python -m pipeline.review_run --input <DXF...> --territory-category dvorovye --proposals proposals.json --output-report review.json
```
Необязательный флаг `--lep-voltage-kv <кВ>` — если реальный класс напряжения ЛЭП с неопределённым по чертежу классом известен из дополнительных материалов, пересчитывает отступ по нему (ПП РФ №160) вместо максимально консервативного (55 м). См. `docs/FEATURES.md`, 2026-09-25.

**Docker** (см. `Dockerfile`, `docker-compose.yml`, `docker/oda/README.md` про опциональный ODA File Converter):
```
docker compose run --rm app python -m pipeline.run --help
docker compose run --rm app python -m pytest tests/ -q
```

**Веб-UI** (второй способ запуска, не замена CLI — см. `docs/TASK_BRIEF.md`): визуализация плана + два режима работы (автогенерация и проверка предложенной человеком посадки drag-and-drop). Swagger/OpenAPI — на `/docs`.
```
uvicorn pipeline.web.app:app --reload          # локально, http://127.0.0.1:8000
docker compose up web                          # в Docker, http://localhost:8000
```
Работает на заранее подготовленных демо-объектах (`data/demo_objects/`) и, с 2026-09-19, на объектах, загруженных прямо в интерфейсе — кнопка «📤 Загрузить свой DWG/DXF» в шапке (несколько файлов сразу, DWG конвертируется через `pipeline/ingest/dwg_convert.py`, требует ODA File Converter на сервере). Обработка синхронная, со спиннером — крупные объекты (десятки гектаров) могут занять несколько минут. Карта + реестр зданий data.mos.ru — отдельная, более поздняя задача.

Если на объекте есть ЛЭП с неопределённым по чертежу классом напряжения — в шапке появляется контрол «Класс напряжения ЛЭП» (выпадающий список из 8 типовых тарифов ПП РФ №160; наведите курсор на подпись — во всплывающей подсказке видно, сколько именно таких объектов на участке). По умолчанию применяется максимально консервативный отступ (55 м); если оператор знает реальный класс из дополнительных материалов — выбор пересчитывает допустимую зону сразу на плане, в автогенерации и в проверке. См. `docs/FEATURES.md`, 2026-09-25.

Печать текущей вкладки (кнопка «🖨️ Печать») и переключатель «Скрыть рекомендации сервиса» — окончательное решение о посадке остаётся за пользователем, но полный ответ сервиса ВСЕГДА сохраняется на сервере, независимо от того, что скрыто на экране.

**Обновление цен из прайс-листа питомника**: панель «ℹ️ Нормативная база» → загрузить .xlsx/.xls/.docx/.pdf → сервис распознаёт категорию каждого растения (точный лукап по каталогу ДПиООС, при неудаче — по родовым словам, выведенным из самого каталога) и предлагает обновлённые цены в таблице предпросмотра — применяется только то, что вы отметите. Изменения пишутся прямо в `data/reference/planting_cost_estimates.yaml` с бэкапом (`data/reference/backups/`, не больше 2).

**Аудит-лог**: каждый вызов `/api/demo-objects/{id}/generate` и `.../review` полностью логируется в `data/web_audit/<UTC-дата>.jsonl` (см. `pipeline/web/audit_log.py`) — не публикуется в git, не выводится ни в одном UI/API, переживает перезапуск контейнера (том `./data:/app/data` уже смонтирован в `docker-compose.yml`).

## Как обновить нормативную базу (без интернета, для закрытой сети)

Все нормативные данные (743-ПП, 623-ПП, 369-ПП, ПП №160 и т.д.) — это обычные файлы `data/reference/*.json`/`*.yaml`, по одному на акт. Никакой сети, облака или специальной команды загрузки не требуется — только замена файла на диске.

1. **Подготовьте новый файл** с тем же именем и той же структурой верхнего уровня, что и текущий — какие поля обязательны для каждого файла, см. таблицу в `docs/DATA_UPDATE_GUIDE.md`.
2. **Замените файл** на месте — `data/reference/<то же имя файла>`. Скопировать поверх старого можно как угодно: вручную, по внутренней сети, с флешки.
3. **Ничего перезапускать не нужно.** Каждый реестр читает свой файл заново на каждый запрос (веб-UI) или на каждый запуск (CLI) — кэша нет, изменения подхватываются сразу.
4. **Проверьте, что файл принят**: откройте кнопку «ℹ️ Нормативная база» в шапке веб-UI (или `GET /api/data-sources`) — там видна дата последнего изменения каждого файла. Если файл повреждён или неправильной структуры — сервис не упадёт молча, а вернёт понятную ошибку с указанием файла и поля.
5. **Прогоните тесты**: `pytest tests/ -q`. Валидация на шаге 4 проверяет только структуру, а не содержимое — если новый файл меняет состав видов/чисел по существу, часть тестов с жёсткими проверками по значениям (например, точный подсчёт видов в каталоге) придётся пересмотреть вручную, автоматически это не решается.

Полный список всех 9 обновляемых файлов, что каждый регулирует и какие поля обязательны — таблица в `docs/DATA_UPDATE_GUIDE.md`.

## Целевая среда

Продукт должен работать на MosTex.OS (Linux). Разработка кросс-платформенная, но финальная проверка — в Docker-контейнере на Linux. Пошаговая инструкция сборки/запуска/проверки именно под эту среду — `docs/MOSTEX_OS_DEPLOYMENT.md`.
