# План агентов/модулей пайплайна

Термин «агент» здесь = отдельный модуль/этап пайплайна с чёткой ответственностью и проверяемым контрактом входа/выхода — не обязательно LLM-агент. Список сгруппирован по фазам, с явной пометкой MVP / Фаза 2.

(Документ изначально группировал агентов по двум сервисам — Service A и вспомогательному Service B ([[ARCHITECTURE]], §0). Service B по решению пользователя (2026-09-24) исключён из объёма проекта, см. `docs/OPEN_QUESTIONS.md` — ниже описан только состав для Service A; агент 2b (Ad-hoc Ingest, был только для Service B) убран из списка целиком.)

### 1. Territory/Case Onboarding Agent
- **Задача**: приём новой папки объекта, проверка комплектности входа, регистрация в реестре — проверяет наличие слоя коммуникаций в DXF, валидность файла, систему координат/масштаб.
- **Выход**: статус объекта (`new`/`validated`/`missing_communications_layer`/`manual_layer_mapping_required`/`unsupported_format_rejected`) + запись в реестре.

### 2. DXF Ingest Agent
- **Задача**: (при необходимости — вызов DWG→DXF конвертации через ODA File Converter, см. [[ARCHITECTURE]] §5, так как реальные тестовые чертежи — DWG, не DXF, см. [[DATA_STRUCTURE]] §3) → парсинг DXF → внутренняя геомодель с типизацией слоёв по словарю алиасов, включая слой дендроплана существующих насаждений.
- Оценивается по ТЗ отдельно на устойчивость к «грязным» DXF.

### 3. Context Builder Agent
- **Задача**: подтянуть кадастр (границы, категория земель, ЗОУИТ) + городской контекст и свести с геомоделью в одну систему координат.

### 4. Constraint/Buffer Engine Agent
- **Задача**: построить буферные зоны отступов по реестру норм, объединить с охранными зонами/ЗОУИТ/застройкой **и с существующими насаждениями, помеченными «сохранить» в перечетной ведомости** ([[DATA_STRUCTURE]] §4) → карта допустимости по типам насаждений.
- Каждая запрещённая/допустимая зона обязана хранить ссылку на конкретный источник — норму **или** конкретную запись ведомости (номер дерева/куста) — без этого нет материала для интерпретируемого отчёта.
- Проверка предлагаемых видов на инвазивность по перечню из ППМ 369-ПП ([[NORMATIVE_REFERENCES]]) — подтверждена как реальная необходимость (в справочнике пород датасета уже встречаются явные записи об инвазивных видах).

### 5. Placement Generator Agent
- Конкретные точки/объекты посадки. Подход для MVP — детерминированные правила/эвристики (не ML), чтобы результат был воспроизводим и объясним по требованию ТЗ.
- **Реализовано (2026-09-15, MVP)**: `pipeline/placement/generator.py`. Сетка-кандидат с шагом из верифицированной 743-ПП/Таблицы 3.6.2, точка — строго внутри допустимой зоны, вид — первый по алфавиту рекомендованный (ДПиООС) и не инвазивный (369-ПП); честный статус `no_recommended_species`, если подходящего вида нет.
- **Дополнено (2026-09-16)** — фитосанитарная совместимость дерева и кустарника: сноска [6] каталога ДПиООС (можжевельник — переносчик ржавчинных грибов — конфликтует с яблоней/грушей/айвой). Вид для второй обрабатываемой формы исключает конфликтующих кандидатов, `PlacementResult.species_conflict_note` фиксирует, что было исключено и почему — видно в JSON-отчёте (`species_choices`). Это единственное правило совместимости с верифицированным источником; более широкая аллелопатия/ярусность и освещённость (теневая сторона) по-прежнему сознательно не учтены — `docs/ARCHITECTURE.md` §3.1c.
- **Многовидовой выбор чек-боксами, добавлен 2026-09-24** (прямой запрос пользователя веб-UI: «список растений с чек-боксами, чтобы пользователь мог сначала задать перечень растений, которые он хочет разместить») — `pick_species_multi()` + `generate_placement(selected_species_names=...)`. Без параметра (по умолчанию) поведение не меняется — один вид, первый по алфавиту (`pick_species`). С параметром — несколько выбранных пользователем видов распределяются по точкам round-robin в алфавитном порядке отфильтрованного набора (детерминированно, без seed); фильтры те же, что и в однвидовом режиме (рекомендован+не инвазивен, перепроверяется заново — чек-бокс не обходит 369-ПП) плюс фитосанитарный конфликт с уже выбранными видами другой формы (`avoid_conflict_with` расширен с одиночного вида до списка). `PlacementResult.chosen_species_entries: list[...]` — новое поле, `chosen_species_entry` сохранён как первый элемент для обратной совместимости. Стоимость считается по каждой точке отдельно (не `count × unit_cost`). Веб-API: `POST /api/demo-objects/{id}/generate` принимает `selected_species: {"tree": [...], "shrub": [...]}`. 7 новых тестов, проверено вживую через Playwright (реальные клики по чек-боксам). **Известная оговорка**: `pipeline/export/dxf_export.py` при выборе хвойное/лиственное для блока-значка по-прежнему смотрит на ОДИН представительный вид, не на вид конкретной точки — см. `docs/LIMITATIONS.md`.
- **Второй режим работы, добавлен 2026-09-18** (прямое решение пользователя: «ЧЕЛОВЕК будет решать, что и где сажать, а ты будешь проверять») — `pipeline/review/placement_review.py` + CLI `pipeline/review_run.py`. ДОБАВЛЯЕТСЯ рядом с автоматическим генератором выше, не заменяет его. Человек предлагает произвольный список (вид + жизненная форма + точка) — формат ввода не привязан к DXF/UI (см. докстринг модуля). Сервис независимо проверяет: вид существует в каталоге ДПиООС (329 видов) и рекомендован для категории; не инвазивен (369-ПП); нет фитосанитарного конфликта (сноска [6]) между ЛЮБОЙ парой предложенных видов (не только дерево/кустарник, как в автогенераторе); отступы от коммуникаций (743-ПП, переиспользует ту же независимую проверку, что и 6.1); густота — и верхняя, и нижняя граница нормы 623-ПП/Таблица В.1 (автогенератор и агент ОТК проверяли только верхнюю); **минимальное расстояние между точками ОДНОГО вида посадки** (743-ПП, Таблица 3.6.2 «групповая посадка» — та же норма, что задаёт шаг сетки автогенератора, добавлено 2026-09-24 по прямому замечанию пользователя, увидевшего в веб-UI два дерева, перетащенных почти в одну точку, без единого замечания — густота считает агрегатное число на площадь, а не расстояние между конкретной парой точек). По решению пользователя — **только честный диагноз со ссылкой на норму, без автоматических исправлений** («сдвиньте точку», «уберите N штук» — вне области этой проверки). 16 тестов (`tests/test_placement_review.py`), проверено на реальном объекте («Песчаный переулок») и вживую через веб-UI API.

### 6. Агент ОТК (технический контроль) — ключевой, по прямому запросу пользователя
Развёрнутое описание — [[ARCHITECTURE]] §3. Здесь — контракт и состав проверок:

- **6.1 Сверка с картографической основой** — независимый пересчёт расстояний напрямую по исходной геометрии, не через внутренние переменные генератора.
  - **6.1a реализовано (2026-09-16)** — `pipeline/otk/boundary_plausibility.py`: независимая проверка правдоподобия площади границы участка относительно bbox всех объектов-коммуникаций. Найдена и обоснована реальным багом (см. [[DATA_STRUCTURE]] §11.3) — эта проверка поймала бы его автоматически.
  - **6.1 (остальная часть) реализовано (2026-09-17)** — `pipeline/otk/offset_compliance.py`: для каждой точки посадки независимый пересчёт фактического расстояния до исходной (небуферизованной) геометрии каждого объекта-ограничения и сравнение с требуемым отступом, без обращения к вычисленному `ConstraintMapResult.allowed_zone`. Пространственный индекс STRtree — производительность на объектах с десятками тысяч объектов-ограничений. Проверено на реальных объектах («Песчаный переулок», «Олимпийская деревня») — 0 нарушений.
- **6.2 Целостность слоёв** — исходные слои DXF геометрически не изменены; результат только в выделенных слоях.
- **6.3 Анти-галлюцинационная проверка обоснований реализовано (2026-09-17)** — `pipeline/otk/citation_integrity.py`: каждая ссылка на норму резолвится в верифицированную запись [[NORMATIVE_REFERENCES]] — пересчитывается заново из свежих `OffsetRegistry`/`DpioosSpeciesCatalog`/`LepZoneRegistry` и сравнивается буквально с тем, что попало в готовый JSON-отчёт. В этом коде текст объяснения и так никогда не формируется генеративной моделью (собирается по шаблону из уже проверенных полей) — проверка ловит не гипотетическую LLM-галлюцинацию, а регрессию (ручную правку в обход шаблонных функций, drift между кодом и реестром). Ключевой инвариант — неверифицированная строка обязана нести честный плейсхолдер, а не подставленный текст.
- **6.4 Регрессия на эталонных данных реализовано (2026-09-17)** — `tests/test_service_a_regression.py`: полный прогон на подтверждённом реальном объекте («Песчаный переулок», см. [[DATA_STRUCTURE]] §11.2), пропускается, если датасет/ODA File Converter недоступны. Повторяемость (5 прогонов, DXF+отчёт идентичны) + golden baseline (площадь границы, число посадок, все проверки ОТК = `ok`). По пути найдено, что ezdxf штампует заголовок DXF (`$TDCREATE/$TDUPDATE/$VERSIONGUID` + служебную запись версии) заново при каждом `saveas()` — метаданные момента сохранения, не решения пайплайна; узкая нормализация перед сравнением, тем же принципом, что и allowlist в 6.2.
- **6.5 Достаточность данных — не применяется**: относилась к неполному входу второго, вспомогательного сервиса (Service B), исключённого из объёма проекта (2026-09-24, см. `docs/OPEN_QUESTIONS.md`).
- **Выход агента**: подтверждённый список / отклонения с причиной + **Протокол технического контроля** (отдельный артефакт, JSON + человекочитаемая часть в общем отчёте) — вердикт по каждой точке/зоне с указанием, какая именно проверка его дала.
- **Принцип независимости**: код ОТК не должен переиспользовать внутренние допущения генератора (иначе он не ловит его же ошибки) — отдельная реализация, отдельные тесты.

### 7. DXF Export Agent
- Запись подтверждённого списка в новые слои (`PLANTING_PROPOSED`, `GREEN_AI`, доп. слои по типу), исходные слои не трогаются. Работает только после положительного протокола ОТК.
- **Реализовано (2026-09-15, MVP)**: `pipeline/export/dxf_export.py` — слои `GREEN_AI_TREE_PROPOSED`/`_REJECTED`, `GREEN_AI_SHRUB_PROPOSED`/`_REJECTED`, POINT+TEXT с id-меткой на точку, запись только в НОВЫЙ файл (защита от перезаписи исходного — явная проверка пути). Работает БЕЗ ожидания протокола ОТК — полного агента ОТК ещё нет, это временное упрощение MVP, а не целевая схема.

### 8. Interpretation Report Agent
- Собирает JSON (обязательно) + человекочитаемый отчёт: посадка/зона → норма → пункт → вывод, плюс визуальная план-схема "до/после" с id-метками (см. [[REPORT_DESIGN]]) и протокол ОТК в человекочитаемом виде.
- **Реализовано частично (2026-09-15, MVP)**: `pipeline/report/interpretation_report.py` — только JSON (обязательный по ТЗ основной формат), с явным `site_boundary_status` и предупреждением при `found_low_confidence`, плюс вердикт агента ОТК (6.1a). Человекочитаемый отчёт, визуальная план-схема, человекочитаемый протокол ОТК — не сделаны на тот момент.
- **Критичный баг найден и исправлен (2026-09-16)**: на реальном объекте (140447 применённых норм) отчёт весил 168 ГБ — нормы копировались в каждую точку вместо хранения один раз на вид посадки. Исправлено, `schema_version` → `1.1-mvp`. См. `docs/SESSION_LOG.md`.
- **Человекочитаемый отчёт реализован (2026-09-24)** — `pipeline/report/human_report.py`, Markdown + HTML (не PDF — сознательное решение, см. `docs/LIMITATIONS.md`), схема «до/после», таблица обоснований, протокол ОТК.

### 9. History Store Agent
- Версионирование прогонов по объекту/запросу, сравнение нового прогона с предыдущим (что изменилось).

## Фаза 2 (продуктовая надстройка — после того, как ядро MVP закрыто и проверено)

### 10. Plant Catalog Agent
- Полноценный справочник видов: глубина и прогнозируемый разлёт корней по годам роста, крона, требования к почве/свету, видоспецифичный минимальный отступ.
- **Сид уже есть**: официальный справочник пород с кодом ценности и компенсационной стоимостью, найден внутри реальных ведомостей датасета (`data/reference/raw_species_directory_strings.txt`, см. [[DATA_STRUCTURE]] §5) — сотни видов, но без данных о корнях/росте. Источник для глубины/прогноза роста корней по-прежнему не найден — см. [[OPEN_QUESTIONS]].

### 11. Individual Object Analysis (режим)
- Тот же пайплайн (агенты 1–8), вызванный для одного произвольного объекта вне пакетного прогона — не новый компонент, а режим вызова.

### 12. Uploaded-Plan Overlay Agent
- Пользователь загружает уже задуманный им план посадок — агент накладывает его на карту допустимости и возвращает, что конфликтует с нормами, а что свободно для альтернатив. Технически — Constraint Engine + агент ОТК, применённые к внешнему вводу вместо собственной генерации.

### 13. Visualization Agent (бонус по ТЗ)
- Фотореалистичный рендер участка после посадки — только после успешного и подтверждённого ОТК DXF.
