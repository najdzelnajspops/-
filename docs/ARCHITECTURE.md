## 1. Общая схема пайплайна

Канонический, актуальный флоучарт (Mermaid) реально реализованного пути — [[PROCESS_FLOWCHART]] (обязательный документ по ТЗ §6.3). Схема ниже — более ранний, словесный набросок компонентов на этапе планирования (Фаза 0); при расхождении между ними в силе [[PROCESS_FLOWCHART]], а не этот раздел.

Путь: DWG/DXF вход → DWG→DXF конвертация (только если пришёл DWG, см. §5) → DXF Ingest → Context Builder (единая геомодель, + существующие насаждения с заключением «сохранить») → Constraint/Buffer Engine (карта «где можно сажать», по реестру норм [[NORMATIVE_REFERENCES]]) → Placement Generator → **АГЕНТ ОТК** (независимая переповерка + сверка с картографической основой, см. §3) → DXF Export (новый слой `GREEN_AI_*`) и Interpretation Report (JSON + человекочитаемый Markdown/HTML, см. [[REPORT_DESIGN]]).

## 3. Агент ОТК (технический контроль) — отдельно, подробно

Это не формальность, а **обязательный блокирующий этап**, отдельный от генератора и не доверяющий его расчётам на слово. Название и роль — по аналогии с реальным отделом технического контроля: ничего не считается «готовым результатом», пока ОТК не подписал протокол.

Четыре независимые проверки внутри агента ОТК:

1. **Сверка с картографической основой** — ОТК заново, независимым кодом, снимает координаты объектов коммуникаций/охранных зон прямо с исходной картографической/геопространственной основы (а не берёт на веру внутренние переменные генератора) и пересчитывает фактическое расстояние до каждой предложенной точки/зоны. Расхождение с тем, что заявил генератор, = блокирующая ошибка, результат не проходит дальше.
2. **Целостность слоёв** — геометрическое сравнение исходных слоёв входного и выходного DXF: должны совпадать; результат обязан лежать только в новых слоях.
3. **Анти-галлюцинационная проверка обоснований** — каждая ссылка на норму в тексте обоснования должна резолвиться в реально существующую, верифицированную запись в [[NORMATIVE_REFERENCES]]. Если использован генеративный компонент (LLM) где-либо в формировании текста объяснения — его вывод **никогда** не идёт в отчёт напрямую: текст обоснования всегда собирается по шаблону из проверенных полей (норма, пункт, дистанция), а не сочиняется свободным текстом. Несуществующий/неверифицированный пункт нормы = блокирующая ошибка, а не «предупреждение».
4. **Регрессия на эталонных данных** — прогон на датасете «Пилотный проект 20 улиц» (когда будет доступен) при каждом изменении констрейнт-движка/генератора, сравнение с эталонным выходом.

**Результат работы ОТК — отдельный артефакт**: «Протокол технического контроля» (JSON + человекочитаемая часть в общем отчёте) — по каждой точке/зоне явный вердикт `подтверждено / отклонено / требует ручной проверки`, с указанием, какая именно из четырёх проверок дала этот вердикт. Ничего не публикуется в финальный DXF/отчёт без прохождения всех четырёх проверок.

(Изначально планировалась пятая функция ОТК — проверка достаточности данных для неполного входа второго, вспомогательного сервиса; сервис исключён из объёма проекта 2026-09-24, см. `docs/OPEN_QUESTIONS.md`, пятая функция не нужна.)

## 3.1 Повторяемость результата (обязательное требование к демо, не факультатив)

Пользователь прямо предупредил (2026-09-15): на питч-сессии жюри может попросить повторить прогон и сверить, что результат не изменился. Это не абстрактное пожелание к качеству кода — это конкретный, проверяемый на демо критерий, и его нарушение выглядит хуже, чем скромный, но стабильный результат.

Практические следствия для всего пайплайна:

1. **Один и тот же вход → один и тот же выход, всегда.** Никакой случайности без фиксированного seed; если где-то используется ML/генеративный компонент — он либо детерминирован по умолчанию, либо запускается с зафиксированным seed, который сохраняется вместе с результатом прогона.
2. **Порядок имеет значение и должен быть стабильным.** Python `set`/`dict` без явной сортировки, порядок чтения файловой системы, порядок сущностей DXF при парсинге — всё это источники "невидимой" недетерминированности. Каждый этап пайплайна (Ingest → Constraint Engine → Placement Generator → ОТК → Export/Report), где формируется список объектов, обязан либо сохранять порядок входа, либо сортировать по стабильному ключу (id/handle/координаты) — не полагаться на порядок обхода неупорядоченных структур.
3. **Данные организаторов вносятся в постоянную базу один раз, а не переобрабатываются на лету при каждом запросе.** Практический вывод из формулировки пользователя «данные нужно сразу внести в базу и отработать так, чтобы результат оказался максимально точным и не менялся от запроса к запросу»: Ingest/Context Builder должны один раз построить и закэшировать внутреннее представление объекта (геомодель, реестр норм на момент прогона), а Placement Generator/ОТК/Export работать от этого зафиксированного состояния — а не пересчитывать geo-контекст или тянуть внешние источники заново при каждом вызове, где результат может незаметно "поплыть" (например, если внешний источник обновился между двумя запросами).
4. **Regression-тест на повторяемость — обязательная часть тестового покрытия**, не опция: см. `tests/test_reproducibility.py` (два независимых прогона с одним и тем же входом обязаны давать геометрически идентичный результат — не "похожий", а `shapely.equals`; порядок пунктов в отчёте интерпретации тоже должен совпадать между прогонами).
5. **На демо**: заранее прогнать выбранный тестовый объект несколько раз локально и держать под рукой оба результата (или скрипт, который это сделает вживую на глазах жюри за секунды) — риск «на демо внезапно другой ответ» выше, чем риск, что решение покажется скромным.
6. **Подтверждено на реальном масштабе (2026-09-16)**: два независимых прогона `run_service_a` на «Олимпийской деревне» (140447 объектов-коммуникаций, 293364 точки размещения) дали ПОБАЙТОВО идентичный JSON-отчёт (SHA-256 совпал). До этого повторяемость была подтверждена только на синтетических тестах (`tests/test_reproducibility.py`) — это первое подтверждение на настоящих данных такого объёма, не на игрушечном примере. Время выполнения при этом стабильно ~330–345 с — см. `docs/OPEN_QUESTIONS.md` про кандидата на оптимизацию.

### 3.1a Кэш — это не то же самое, что алгоритмическая детерминированность (важное разграничение)

Пользователь верно указал на уязвимость в исходной формулировке: «записывать результат первого прогона, чтобы не ошибиться при повторе» — это **не решает** задачу повторяемости, если под этим понимается «на любой ПОВТОР одного и того же исходного входа мы просто отдаём закэшированный ответ, а не пересчитываем». У такого подхода два разных провала:

- жюри попросит прогнать **новый** тестовый объект (не тот, что был закэширован) — кэш здесь не поможет вообще, поможет только реально детерминированный алгоритм;
- жюри попросит объяснить **как** обеспечена повторяемость — «мы один раз посчитали и сохранили ответ» не является ответом на вопрос «ваш алгоритм детерминирован?», это ответ на вопрос «умеете ли вы мемоизировать функцию», что не одно и то же и не то, что спрашивается.

Поэтому правильное разделение (и это то, что реально реализовано, а не декларативно заявлено):

- **Кэшируется** — разобранное представление входа (Ingest: геомодель участка, реестр норм, версия используемых сидов) — это фактические данные объекта, которые не должны молча меняться между прогонами (например, если открытый источник обновился) — это чистая инженерная гигиена, не имеет отношения к доказательству детерминированности.
- **Не кэшируется, а реально пересчитывается каждый раз** — сам расчёт: Constraint Engine строит буферы заново из геометрии при каждом вызове (см. `pipeline/constraints/buffer_engine.py` — там нет ни одного `lru_cache`/сохранённого файла с готовым ответом), и `tests/test_reproducibility.py` проверяет именно это: два **независимых, полных** вызова `build_constraint_map()` — не «вызов и чтение сохранённого результата», а два реальных прогона алгоритма — дают идентичный результат.

### Текущий статус доказательства (честно, без завышения)

Что реально проверено на 2026-09-15 (13/13 тестов, `pytest tests/ -q`):
- Constraint/Buffer Engine детерминирован **в рамках одной среды** (эта Windows-машина, shapely 2.1.2 + GEOS 3.13.1, версии зафиксированы `==` в `requirements.txt` не просто из формальности, а потому что GEOS/shapely по-разному считают буферы/объединения между версиями — см. комментарий в `requirements.txt`), включая на намеренно нагруженной геометрии (25 повторов на 40 пересекающихся/касающихся буферов, не только на тривиальном случае).
- Параметр аппроксимации окружности при buffer() (`quad_segs`) зафиксирован явно в коде (`BUFFER_QUAD_SEGS = 16`), а не оставлен на дефолт библиотеки, который менялся между версиями shapely.

**Обновление 2026-09-15 — кросс-платформенная проверка пройдена, не гипотетически**: пользователь предоставил доступ к WSL Ubuntu 26.04 на своей машине. Установлены те же зафиксированные версии зависимостей (`pip install -r requirements.txt`, без sudo — через `get-pip.py --user --break-system-packages`, т.к. системный apt требовал пароль, которого у ассистента нет и не должно быть). Результат:
- `shapely.geos_version` на Linux — `(3, 13, 1)`, **то же самое**, что на Windows-машине разработки — совпадение не гарантировано в общем случае (разные wheel-сборки для разных платформ могут вендорить разные версии GEOS), но в данном случае подтверждено фактически, не предположено.
- Полный набор тестов (13/13, включая адверсарный) зелёный на Linux так же, как на Windows.
- Отдельно, вне pytest — `tests/cross_platform_dump.py` прогнан на обеих платформах, вывод (WKT допустимой/запрещённой зоны, площадь, полный текст отчёта с цитатами) сверен через `diff --strip-trailing-cr` — **побайтово идентичен** (единственная разница была в стиле окончания строк CRLF/LF, что ожидаемо и не имеет отношения к вычислениям). Это не «оба теста прошли», а прямое сравнение фактического вывода.

Что это доказывает: Constraint Engine в текущем виде даёт идентичный результат на Windows (dev) и на реальном Linux (Ubuntu, той же кодовой базой GEOS, что должна быть и в Docker-образе на MosTex.OS). Что это **не закрывает** полностью:
- Проверка была на Ubuntu через WSL, а не внутри самого Docker-образа проекта (Dockerfile ещё не написан) — по духу это то же Linux-ядро и то же пространство пользователя, но финальная сверка «именно в контейнере» — отдельный пункт чек-листа, когда Dockerfile появится.
- **Placement Generator** (алгоритм выбора конкретных точек посадки внутри допустимой зоны) ещё не написан — это компонент с наибольшим реальным риском недетерминированности (порядок обхода сложной геометрии, тай-брейки при равных расстояниях), и ни синтетические тесты, ни кросс-платформенная сверка его пока не покрывают, потому что покрывать нечего.
- **Реальный DXF/Excel Ingest** ещё не написан — обход файловой системы, порядок сущностей DXF/строк Excel тоже надо будет явно тестировать на повторяемость (в т.ч. кросс-платформенно), не полагаться на «наверное, само сойдётся».

## 3.1b Ограничение: модель только 2D, без глубины и без видовой дифференциации корней (важно, не мелким шрифтом)

Зафиксировано по прямому вопросу пользователя (2026-09-15). Constraint Engine считает отступы **только в горизонтальной плоскости (X/Y)**. Это не недоработка, которую забыли сделать — это осознанная граница того, что вообще можно построить из имеющихся данных и норм:

- **У коммуникаций нет глубины в данных**: DXF показывает трассу в плане (вид сверху), глубина заложения — в профилях/разрезах, отдельных документах, которых нет в текущем контуре Ingest.
- **У растений нет данных по глубине/типу корневой системы**: нет источника (см. §про Plant Catalog в [[AGENTS_PLAN]], Фаза 2 — не закрыто с самого начала проекта).
- **743-ПП, источник наших цифр, сама по себе не требует 3D** — Таблица 3.6.1 даёт готовое горизонтальное расстояние (например, 2 м от кабеля для дерева), уже профессионально откалиброванное под типичную глубину/разлёт корней. Это отраслевой стандарт подхода, не наше упрощение.

**Что из этого следует практически**: отступ **одинаков для любого растения внутри категории «дерево»/«кустарник»**, независимо от вида. Куст с компактным корневым комом и куст с агрессивной, склонной прорастать к трубам корневой системой (классические примеры — ива, тополь) получают одну и ту же норму. Это реальный, непокрытый на 2026-09-15 риск, а не гипотетический.

**Решение по объёму (согласовывается с пользователем, не решено односторонне)**: полноценное 3D-моделирование глубины не рекомендуется — данных для этого нет ни по сетям, ни по растениям, и норма этого не требует. Более реалистичный путь — точечная надбавка к отступу для ИЗВЕСТНЫХ агрессивных видов, явно помеченная как практическое допущение (`verified=False`, по аналогии с `existing_vegetation_buffer_policy.yaml`), а не как часть 743-ПП. Требует источника по видам (см. [[OPEN_QUESTIONS]]).

## 3.1c Ограничение: более широкая совместимость посадок и освещённость (тень от зданий) не учитываются

Зафиксировано по прямому вопросу пользователя (2026-09-15). Placement Generator (`pipeline/placement/generator.py`) размещает точки-кандидаты в основном независимо друг от друга. Из двух факторов один частично закрыт, один — нет:

- **Фитосанитарный конфликт (сноска [6] ДПиООС) — реализовано (2026-09-16)**: можжевельник (переносчик ржавчинных грибов) исключается из выбора, если для другой жизненной формы того же участка уже выбрана яблоня/груша/айва (восприимчивый хозяин), и наоборот — см. `species_conflict_reason()` в `pipeline/catalog/dpioos_species_catalog.py`, интеграция в `pipeline/placement/generator.py`/`pipeline/run.py`. Это единственное правило совместимости с верифицированным источником — реализовано только оно, не полная теория аллелопатии/ярусности.
- **Теневая сторона зданий / светолюбие вида — по-прежнему НЕ реализовано.** Для этого не хватает данных с обеих сторон: (а) ориентации/контура зданий из геоподосновы, чтобы понять, где именно тень, и (б) параметра светолюбия/теневыносливости по виду — в каталоге ДПиООС такого параметра нет вообще (только пригодность по категории территории и 7 причин-ограничений, свет не входит). Источника нет — не реализуется, пока он не появится.

**Почему фитосанитарный конфликт сделан, а не отложен, как планировалось изначально**: пользователь напрямую поднял вопрос обоснования конкретной конфигурации посадок (не просто «какой-то вид разрешён», а «почему именно этот, а не другой равно допустимый») — это прямо совпадает с требованием ТЗ п.3 («объяснение почему здесь можно/нужно сажать именно этот тип насаждения») и критерием оценки «качество интерпретируемости». Источник (сноска [6]) уже верифицирован и не требовал нового сбора данных — низкая стоимость, прямое попадание в критерий. Более широкая совместимость (общая аллелопатия/ярусность без цитируемого источника) сознательно НЕ добавлена — риск скатиться в неверифицированную ботаническую теорию (тот же класс проблемы, что и с присланным пользователем текстом стороннего ИИ ранее в этой сессии, см. `docs/NORMATIVE_REFERENCES.md`).

**Дополнено (2026-09-16) — честный ответ на «почему именно этот вид, а не другой равно допустимый»**: `PlacementResult.eligible_alternatives` теперь несёт имена ВСЕХ остальных видов, прошедших те же фильтры (рекомендован, не инвазивен, не конфликтует), кроме выбранного, плюс `TIE_BREAK_EXPLANATION` — явный текст о том, что источник не даёт критерия предпочесть один вид другому среди них, и алфавитный порядок используется только как детерминированный тай-брейк для воспроизводимости, а не как содержательное предпочтение. Видно в JSON-отчёте (`species_choices[].eligible_alternatives`/`tie_break_explanation`) и в CLI-выводе `pipeline/run.py`. Это честно закрывает половину вопроса пользователя («почему этот, а не другой») — вторая половина («почему такая конфигурация в целом», за пределами одной точки) по-прежнему не реализована, см. пункт выше.

## 3.2 Геопривязка — рекомендована, не обязательна (уточнено с пользователем)

Пользователь подтвердил (2026-09-15): это тестовое задание в закрытой среде, поэтому работа в локальной системе координат чертежа (см. [[DATA_STRUCTURE]] §9) допустима. Но **реальная геопривязка (МСК-77 или аналог) даёт более точное определение участка, что напрямую влияет на корректность расположения зон** (кадастр, ЗОУИТ, охранные зоны ЛЭП которые не считаны с самого чертежа) — поэтому это не блокер MVP, но приоритетное направление доработки, а не факультативная функция «когда-нибудь». Если для конкретного тестового объекта координаты геодезических опорных точек читаемы с чертежа (см. [[DATA_STRUCTURE]] §9) — стоит попытаться их использовать уже в MVP, а не откладывать в Фазу 2 по умолчанию.

## 4. Развёртывание

- Единый `Dockerfile` (Python-контейнер на базе Ubuntu/Debian slim — совместим с MosTex.OS/Linux).
- `docker-compose.yml` для локального прогона (пайплайн + опциональный HTTP API).
- Точка входа — CLI-скрипт (`python -m pipeline.run --input <файлы> --base-dxf <файл> --territory-category <категория> --output-dxf <файл> --output-report <файл>`), достаточная по ТЗ; веб-UI — опционально, второй итерацией.
- Если появится HTTP API — обязательное авто-документирование OpenAPI/Swagger.

## 5. Технологический стек (черновой, стек по ТЗ не регламентирован)

- **DWG→DXF конвертация**: **ODA File Converter** (Open Design Alliance, бесплатный официальный конвертер, есть сборка под Linux/Debian — совместимо с MosTex.OS) — вызывается как внешний процесс перед `DXF Ingest`, см. [[DATA_STRUCTURE]] §3.
- **DXF чтение/запись**: `ezdxf` (чистый Python, кросс-платформенный, умеет работать со слоями; **не читает бинарный DWG напрямую** — отсюда обязательность шага конвертации выше).
- **Геометрия/буферы**: `shapely` (буферы отступов, пересечения зон, проверка расстояний).
- **Excel/DOCX/PDF (прайс-листы питомников)**: `openpyxl`/`python-docx`/`pymupdf` — не для входа основного пайплайна, а для загрузки прайс-листа через веб-UI и обновления `data/reference/planting_cost_estimates.yaml` (`pipeline/catalog/price_list_ingest.py`, см. `docs/CHECKLIST.md`); парсер должен быть терпим к тому, что реальные файлы — это не чистые таблицы, а вёрстка с шапкой/объединёнными ячейками/встроенным справочником на том же листе (см. [[DATA_STRUCTURE]] §5).
- **Кадастр/геоданные**: адаптация ранее подготовленных наработок (см. `docs/reference_snippets/`).
- **Отчёт/интерпретируемость**: Jinja2 → Markdown/PDF (см. [[REPORT_DESIGN]]).

## 6. Границы MVP

**В MVP:**
- Конвертация DWG→DXF (реальные тестовые чертежи почти наверняка в DWG).
- Импорт DXF тестового участка.
- Расчёт буферных зон отступов минимум по одному нормативному источнику — расширение по мере верификации пунктов.
- Учёт существующих насаждений с заключением «сохранить» как отдельного источника ограничений (данные реально есть в датасете — «Перечетная ведомость», не гипотеза).
- Генерация плана посадки минимум для одного типа насаждений на отдельном слое.
- Экспорт в DXF без порчи исходных слоёв.
- Агент ОТК (проверки 1–4) — обязателен, не опция.
- Отчёт интерпретации (минимум JSON) со ссылкой на норму по каждой точке + визуальная схема.
- CLI запуск, Docker-упаковка.

(Изначально здесь планировался промежуточный шаг «минимальный Service B» между MVP и Фазой 2 — второй, вспомогательный сервис Ad-hoc-загрузки Excel/PDF/DOCX без DXF-подосновы. По решению пользователя (2026-09-24) исключён из объёма проекта, см. `docs/OPEN_QUESTIONS.md`.)
