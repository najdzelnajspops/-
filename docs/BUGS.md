## 2026-09-24 — Проверка человеческого выбора не ловила два растения одного вида, посаженных почти в одну точку

Пользователь вживую в веб-UI перетащил два дерева на расстояние 0.54 м друг от друга и нажал «Проверить» — ни одного замечания. Причина: 4 существующие проверки (`pipeline/review/placement_review.py`) — вид/каталог, фитосанитарный конфликт, отступ от коммуникаций, густота (агрегатное число посадок на площадь) — ни одна из них не сравнивает расстояние между двумя КОНКРЕТНЫМИ точками одного вида посадки. Автогенератор эту норму (743-ПП, Таблица 3.6.2, ~6 м для дерева) соблюдает по построению (шаг сетки), но для ручного ввода этой симметрии не было. Исправлено: добавлена 5-я проверка `_check_minimum_spacing`. Подробности — `docs/SESSION_LOG.md`, `docs/CHECKLIST.md`.

## 2026-09-24 — CLI падал с UnicodeEncodeError при перенаправлении вывода в файл на Windows

Обнаружено при добавлении нового демо-объекта («Грузинская М ул», не вошёл в демо-набор по отдельной причине — см. ниже): `python -m pipeline.run ... > log.txt` падал с `UnicodeEncodeError: 'charmap' codec can't encode character '\xb2'`. Причина: символ «²» (U+00B2, надстрочная двойка в «м²») отсутствует в cp1251 — кодировке, в которую Python на этой машине сериализует stdout при перенаправлении в файл (не в реальную консоль). Затрагивало явные строки в `pipeline/otk/boundary_plausibility.py` (пояснение проверки 6.1a) и `pipeline/review/placement_review.py` (пояснения `density_too_high`/`density_too_low`) — падало при печати ЛЮБОГО из этих сообщений, не только на конкретном объекте. Исправлено — везде в пользовательских сообщениях «м²» заменено на «кв. м» (без спецсимвола). Реальный практический риск: живая демонстрация жюри с перенаправлением вывода в лог-файл могла упасть на любом объекте с нетривиальным замечанием ОТК/густоты.

Проверено вживую через реальный ярлык, не только напрямую через `.bat`.

## 2026-09-24 — При категории «Парки» точки-кустарники визуально «вылезали» за пределы разрешённой зоны

Жалоба пользователя со скриншотом: «если ставишь парки и бульвары, то при автоматической генерации он вылезает за пределы разрешенной зоны». Это НЕ ошибка размещения — `generate_placement()` принимает точку только строго внутри `allowed_zone` (`shapely.contains`), выход геометрически невозможен. Реальная причина — неполная отрисовка на фронтенде: `pipeline/web/static/app.js::drawBasePlan` рисовал на плане только `allowed_zone.tree`, а точки кустарника кладутся в СВОЮ, отдельно посчитанную `allowed_zone.shrub`, которая почти всегда шире зоны дерева (у кустарника отступы от коммуникаций/построек по 743-ПП меньше, чем у дерева, местами не заданы вовсе). На демо-объекте «Песчаный переулок»: зона кустарника 357.75 м² против зоны дерева 219.14 м² — 138.6 м² легитимно допустимой для кустарника площади оставались на плане незакрашенными. CSS-переменная `--allowed-shrub` для второй зоны была объявлена, но никогда не использовалась — недособранная возможность. У категории «Парки» одна из САМЫХ ВЫСОКИХ норм густоты кустарника (623-ПП: 800-1000 шт/га против 400-720 у большинства других категорий), поэтому расхождение стало массово заметным именно на ней — на категориях с низкой густотой кустарника тот же геометрический зазор существовал, но почти не давал видимых точек. Исправлено — на плане теперь рисуется и зона кустарника (`--allowed-shrub`, под зоной дерева), легенды обеих вкладок дополнены соответствующей строкой. Логика размещения не менялась. **Проверено на всех 8 категориях территории × всех 3 демо-объектах** (24 комбинации, без веб-слоя): расхождение зон геометрическое и одинаковое для всех категорий на одном объекте, не специфично для «Парков» — на «Макеева С. ул» разница доходит до 7427 м² (в разы больше, чем на объекте, где баг был впервые замечен). Фикс закрывает проблему для всех категорий разом. Подробности и живая проверка — `docs/SESSION_LOG.md`, `docs/CHECKLIST.md`.

## 2026-09-27 — `/generate` на реальном плотном объекте: 200 сек и 67,6 МБ ответа

Пока подбирали конфигурацию VPS для сдачи кейса, замерил реальный запрос на демо-объекте «Макеева С. ул» (9,3 га, 104 130 объектов-ограничений в исходных DXF) — оказалось, что этот же запрос (не гипотетический, реальный демо-объект из трёх штатных) выполняется **200 секунд** и весит **67,6 МБ**. Разобрал по стадиям (cProfile) и нашёл три независимых источника, все — на одном и том же реальном объекте:

**1) `applied_constraint_norms_by_kind` — 53 МБ из 67 МБ, одна строка на каждый физический объект-ограничение.** Поле уже один раз лечили от похожего класса проблемы (2026-09-16, дублирование НА КАЖДУЮ ТОЧКУ посадки — 168 ГБ, см. комментарий в `pipeline/report/interpretation_report.py`). На этот раз проблема была ВНУТРИ самого поля: 80 840 (дерево) + 55 686 (кустарник) `zone_sources`, и почти все с одинаковым `boundary_type`/`distance_m`/`citation` (один и тот же газопровод физически состоит из тысяч коротких DXF-сегментов, у каждого — своя строка). Исправлено — `ConstraintMapResult.to_report_rows()` (`pipeline/constraints/buffer_engine.py`) группирует по уникальной норме (тип границы + отступ + верификация + цитата) вместо строки на каждый объект, добавлено поле `feature_count`. Интерпретируемость не потеряна — каждая РАЗЛИЧИМАЯ норма (например, разные классы напряжения ЛЭП) остаётся отдельной строкой. Новый тест — `tests/test_interpretation_report.py::test_identical_norms_are_grouped_not_repeated_one_row_per_feature` (50 000 идентичных объектов → 1 строка).

**2) `check_boundary_plausibility` считал полный `unary_union()` ради одного лишь bounding box.** `pipeline/otk/boundary_plausibility.py` — независимая проверка ОТК 6.1a сравнивает площадь границы участка с bbox всех объектов-коммуникаций, но раньше для этого строился ПОЛНЫЙ геометрический union всех 104 130 объектов, хотя bbox объединения математически идентичен bbox, собранному из min/max отдельных `bounds` (объединение не меняет общий охват — не приближение, тот же результат). Исправлено — прямая агрегация `bounds` вместо `unary_union(...).bounds`: **30 сек → 1,3 сек** на том же объекте.

**3) Constraint Engine буферизовал и объединял ВСЕ объекты, включая заведомо не влияющие на итог.** Реальные DXF нередко содержат коммуникации далеко за пределами самого участка (тот же класс явления, что и раздутый bbox у «Кустанайской улицы», `docs/DATA_STRUCTURE.md` §11.5) — на «Макеева» из 104 130 объектов только ~46 400 лежат в пределах 60 м от границы участка, остальные ~57 700 физически дальше максимально возможного отступа (10 м по 743-ПП, 55 м по ЛЭП) и не могут повлиять на итоговую зону ни при каких обстоятельствах — не приближение, точный геометрический факт. Исправлено — `build_constraint_map()` (`pipeline/constraints/buffer_engine.py`) добавляет пространственный пре-фильтр перед `buffer()`/`unary_union()`: порог считается динамически (`OffsetRegistry.max_known_distance()` — новый метод — плюс фактические `explicit_distance_m` на входе, с запасом ×2), не захардкожен. `unknown_boundary_types`/`skipped_features` не затронуты — пре-фильтр применяется только к самой буферизации, а не к учёту неизвестных типов норм (иначе редкий тип, встретившийся только у дальнего объекта, тихо исчез бы из отчёта). Новый счётчик `features_excluded_by_spatial_prefilter` на `ConstraintMapResult` — для диагностики/тестов, не раздувает отчёт (одно число, не запись на объект). Новые тесты — `tests/test_buffer_engine.py::test_offset_registry_max_known_distance`, `test_spatial_prefilter_excludes_far_features_without_changing_result` (доказывает byte-for-byte идентичный `allowed_zone`/`forbidden_zone` с дальним объектом и без него).

**Итог на реальном объекте «Макеева С. ул»** (проверено на изолированном тестовом порту, рабочий сервер пользователя на 8000 не тронут):

| | Время | Размер ответа |
|---|---|---|
| До фикса | 200 сек | 67,6 МБ |
| После (1) | 125 сек | 390 КБ |
| После (1)+(2)+(3) | **49,7 сек** | 390 КБ |

Заодно перепроверены остальные два демо-объекта: «Багрицкого улица» (меньше по площади) — 27,2 сек; «Песчаный переулок» (основной, вероятно, для живой демонстрации) — 8,5 сек, был быстрым и остался быстрым.

Полный `pytest tests/ -q` — 190/190 (было 188, +2 новых теста; правки затрагивают ядро расчёта допустимой зоны — прогонялся дважды на промежуточных шагах, оба раза зелёный).

## 2026-09-27 — Открытый список «Категория территории» обрезался краем экрана на небольших мониторах

Жалоба со скриншота (15" ноутбук): открытый выпадающий список «Категория территории» обрезается правым краем экрана, длинные названия («Магистрали...», «Территории производственного назначения...») читаются не полностью. Причина — тот же корень, что и у более раннего фикса ширины ЗАКРЫТОГО select (2026-09-24, комментарий в `style.css` строка 86-91): Chromium считает ширину нативного `<select>`/его выпадающего списка по САМОМУ ШИРОКОМУ `<option>`, без переноса строк — `max-width: 340px` у закрытого select ограничивает только его собственную ширину, но не ширину открывающегося поверх списка, и CSS-способа ограничить/перенести текст в нативном выпадающем списке нет ни в одном браузере (кроме экспериментального Chrome `customizable select`, не готов для продакшена). На узких экранах список у самых длинных категорий физически шире доступного места и обрезается краем окна/экрана, не переносясь и не сдвигаясь.

Исправлено — `#demo-select`/`#category-select` дополнены собственным JS-слоем (`enhanceSelect()` в `pipeline/web/static/app.js`): нативный `<select>` остаётся в DOM скрытым (по-прежнему источник `.value`/события `change`, вся остальная логика приложения не изменена), поверх него — кнопка + список с переносом текста (`white-space: normal`) и позиционированием, которое всегда укладывается в границы окна (`position: fixed`, ширина `min(440px, окно-16px)`, сдвиг влево/вверх при нехватке места). `#lep-voltage-select` не трогали — его варианты короткие, риска нет, это единственная нетронутая часть UI, специально не задетая, чтобы не рисковать уже отлаженным контролом.

**Уточнение по этой же правке (тем же днём, по скриншотам пользователя)**: у нового списка сразу нашлись два визуальных недочёта — (1) видимый зазор между кнопкой и открывшимся списком (был явный отступ `+4px` в коде позиционирования) и (2) ширина списка считалась от содержимого (`max-width: min(440px, ...)`), а не от ширины самой кнопки, из-за чего список получался шире/уже кнопки и не совпадал с ней по краям. Исправлено — `positionMenu()` теперь ставит список вплотную к кнопке без отступа и явно выставляет `menu.style.width` равным ширине кнопки (`getBoundingClientRect().width`), а не собственному `max-width`; добавлено скругление стыкующихся углов (`data-menu-open="down"/"up"` в `style.css`) — кнопка и список читаются как один блок. Проверено Playwright: `gap: 0`, `width_diff: 0` для обоих select-ов на 1366×768.

**Ещё одно уточнение той же правки (по скриншоту при уменьшении масштаба страницы)**: на узкой ширине список переносил слова ПОСЕРЕДИНЕ («Общеобразовательн» / «ые и спортивные...») — причина: `overflow-wrap: anywhere` у `.custom-select-option` разрешает разрыв в любом месте, даже когда перенос по границе слова прекрасно уместился бы. Заменено на `overflow-wrap: break-word` (+ явный `word-break: normal`) — перенос теперь только по границе слова, разрыв самого слова остаётся резервным вариантом на случай, если слово само по себе шире строки (в названиях категорий такого нет). Проверено Playwright на принудительно суженной до 210px кнопке — «Общеобразовательные и спортивные учреждения (школы, колледжи)» переносится по словам, без разрывов. Полный `pytest tests/ -q` — 187/187 (правка чисто CSS, бэкенд не затронут).

**Настоящая причина найдена только следующим проходом** (пользователь: «проблема с переносом слов осталась», без нового скриншота) — предыдущая правка (`break-word`) была необходимой, но не достаточной, и маскировала два отдельных дефекта:

1. **Двойное масштабирование при зуме страницы.** Ширина списка считалась в JS через `getBoundingClientRect()` кнопки (уже ОТРИСОВАННое, то есть с учётом текущего масштаба, значение) и подставлялась кнопке как обычный `px`-width — при зуме страницы (`document.documentElement.style.zoom`/Ctrl+/-) это значение масштабировалось ВТОРОЙ раз при отрисовке самого списка. Проверено Playwright (`document.documentElement.style.zoom`): при zoom=1.25 список получался 307.8px против кнопки 246.2px, при zoom=0.75 — наоборот, уже кнопки. Исправлено — ширина/позиция списка больше не считаются в JS пикселями, а заданы чистым CSS (`position: absolute` относительно `.custom-select-wrap`, `width: 100%`, `top: 100%`/`bottom: 100%`) — теперь список физически не может разъехаться с кнопкой ни при каком масштабе, JS оставляет только выбор направления вниз/вверх.
2. **Список, соответствующий по ширине КОРОТКОМУ выбранному названию, был у́же самого длинного слова в остальных вариантах.** Обнаружено даже при 100% zoom без какого-либо масштабирования: у категории «Дворовые территории» кнопка (и значит список) — 196.95px, а слово «Общеобразовательные» (в другом варианте того же списка) физически шире этой колонки — `break-word` в такой ситуации обязан резать слово, других вариантов у него нет. Это и есть настоящий источник жалобы, а не сам зум — зум лишь один из способов её случайно заметить. Исправлено — `.custom-select-menu` получил `min-width: 230px` (по самому длинному реальному слову категорий + отступы): список остаётся РОВНО той же ширины, что и кнопка, везде, где кнопка не уже этого порога, и лишь немного шире — только у коротких названий, чтобы не резать слова.

Проверено Playwright на 100% zoom (корневая причина) и повторно на zoom 0.5-2.0 — переносы везде по словам, ширина списка либо точно равна кнопке, либо (только у коротких названий) немного больше по продуманному минимуму, никогда не по ошибке масштабирования.

**Проверено** через Playwright на 1366×768 и 1024×700 (два реалистичных небольших разрешения): список полностью укладывается в окно на обеих ширинах, выбор категории по-прежнему меняет `state.territoryCategory` и перезагружает геометрию (`native select value after click: parki`), ошибок в консоли нет, список закрывается после выбора. Порт 8000 (сервер пользователя) не перезапускался — проверка на отдельном headless-браузере поверх уже работающего сервиса.

## 2026-09-25 — Сервис не подстраивался под широкий монитор, «папки» отклеивались от окна чертежа

Жалоба со скриншота на 32" мониторе: рабочая область занимает малую часть широкого окна, плюс отдельно — «папки не прикреплены к окну чертежа». Один и тот же корень: `.layout` (карточка плана+панели) была зажата в `max-width: 1400px; margin: 0 auto` (наследие исходного каркаса, не пересмотрено при более ранних правках отзывчивости самого плана), а `.tabs` (полоска вкладок, добавлена позже) — без ограничения ширины, во всю ширину окна с тем же `padding: 115px`. На узких экранах оба случайно совпадали по левому краю, на широких — расходились (на 2516px расхождение 558px). Исправлено — убран `max-width`/`margin:auto` у `.layout`, теперь оба контейнера ведут себя идентично на любой ширине. Побочный эффект (желаемый): область плана растёт вместе с экраном вместо упора в потолок 1400px. Проверено вживую Playwright на ширине 2516px (порт 8000 не тронут) — вкладки и карточка плана точно совпадают по краю. Отдельная часть той же жалобы («хедер растягивается, кнопка "Нормативная база" улетает за край») — НЕ подтверждена: исчерпывающая проверка на 33 ширинах (1240-3440px) и с симуляцией фолбэк-шрифта overflow не воспроизвела. Требуется `window.innerWidth` от пользователя — вероятная причина в масштабировании экрана Windows на 32" мониторе, которое не видно по пиксельным размерам скриншота. Подробности — `docs/SESSION_LOG.md`.

## 2026-09-28 — Окно чертежа и «Ваши посадки» не совпадали по высоте на больших экранах

Жалоба со скриншота на большом мониторе: карточка плана (`.plan-wrap`) заметно выше карточки «Ваши посадки» (`.side-panel`), справа остаётся пустое пространство. Причина: обе карточки — соседние ячейки одной grid-строки (`.tab-panel.active { display: grid; grid-template-columns: 1fr 340px; }`), грид по умолчанию растягивает обе ячейки на высоту строки — но `.side-panel` имел собственный `max-height: 80vh`, независимый от высоты соседней колонки. Как только реальная высота плана превышала 80% высоты вьюпорта (обычное дело на больших мониторах — план 1fr растёт вместе с шириной, а часто и высотой окна), `.side-panel` упирался в свой потолок раньше, чем достигал высоты плана — грид не мог дорастянуть его дальше.

Исправлено — `max-height: 80vh` заменён на `height: 100%` (`pipeline/web/static/style.css`): высота теперь берётся не от вьюпорта независимо, а от уже растянутой grid-строки, то есть буквально равна высоте окна чертежа при любом размере экрана. `overflow-y: auto` оставлен — если содержимое («Ваши посадки»/список замечаний) не помещается даже в эту высоту, панель по-прежнему скроллится сама, просто от той же базовой высоты, что и план.

Проверено Playwright на 2374×1146 (размер экрана из жалобы): `plan_height`/`side_height` до фикса — 988.09px/916.8px (`.side-panel` упирался ровно в 80vh=916.8px), после фикса — 988.09px/988.09px, совпадают точно. Правка чисто CSS, `pytest tests/ -q` не запускался — бэкенд не затронут.
