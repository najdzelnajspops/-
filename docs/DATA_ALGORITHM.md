# Алгоритм: последовательность данных, сопоставление, выдача ответа, добавление новых территорий

Это рабочий документ — детализирует [[ARCHITECTURE]] до уровня «шаг за шагом». Обновляется по мере поступления реальных примеров. **Обновлено после изучения реального датасета** («Пилотный проект 20 улиц» — 20 объектов, см. [[DATA_STRUCTURE]]) — часть допущений ниже заменена на то, что реально наблюдается в данных, а не на предположения.

(Документ изначально описывал общий путь для двух сервисов — Service A (DWG/DXF-слой по ТЗ) и вспомогательного Service B (PDF/Excel/DOCX/опц. GeoJSON, разовая рекомендация). Service B по решению пользователя (2026-09-24) исключён из объёма проекта, см. `docs/OPEN_QUESTIONS.md` — шаги ниже приведены к одному сервису.)

## Этап 0 — Приём территории/запроса (Onboarding)

1. Пользователь/оператор кладёт папку объекта в `data/raw/<id_объекта>/`. **Реальная структура папки объекта неоднородна** между разными улицами (разные названия разделов — «Исходные данные»/«ИСХОДНЫЕ ДАННЫЙ»/«Архивы», «Проектное решение»/«Проектные решения») — см. [[DATA_STRUCTURE]] §1. Onboarding Agent матчит содержимое по типу файла и смыслу, а не по точному имени папки.
2. **Валидация комплектности** (Onboarding Agent, [[AGENTS_PLAN]]): если пришёл DWG — сначала конвертация в DXF (ODA File Converter, см. [[ARCHITECTURE]] §5), затем проверка: валиден ли DXF, есть ли слой(и) коммуникаций, есть ли дендроплан существующих насаждений, определена ли система координат/масштаб (нужно для расчёта отступов в метрах).
3. **Геопривязка** — присвоение реальных координат/CRS (см. блок ниже «Нужна ли геопривязка»).
4. Объект/запрос регистрируется в реестре (`data/reference/objects_registry.*`) со статусом: `new` → `validated` → `ready_for_pipeline` → `processed` → `verified`.

## Этап 1 — Ingest (разбор входных данных)

1. (Если нужно — конвертация DWG→DXF) → парсинг DXF → внутренняя геомодель: геометрия + атрибуты слоя (тип сети — по словарю соответствия имён слоёв, который строится по реальным примерам из датасета). Отдельно разбирается дендроплан существующих насаждений, если он есть в составе объекта.
2. Определение границ участка (из геоподосновы/кадастра, если не размечено явно).
3. Подтяжка кадастровых данных по координатам границы — категория земель, ЗОУИТ (если участок пересекает такую зону — отдельный источник ограничений, не только «отступ от трубы»).
4. Подтяжка городского контекста (застройка, улицы, транспорт) — по открытым геоданным/подоснове.
5. **Разбор существующих насаждений**: если есть перечетная ведомость — извлечение записей с заключением `сохранить`/`вырубить`/`пересадить`; записи `сохранить` идут в Constraint Engine как отдельный источник ограничений (см. Этап 2).
6. Итог этапа — единая внутренняя геомодель: коммуникации (в объёме, который реально известен) + границы + среда + ЗОУИТ + сохраняемые насаждения, в одной системе координат.

## Этап 2 — Построение карты ограничений (Constraint/Buffer Engine)

1. Для каждого объекта коммуникации в геомодели — определить применимую норму отступа: тип сети → таблица «тип сети → минимальный отступ → источник нормы» ([[NORMATIVE_REFERENCES]]).
2. При отсутствии в реестре точного верифицированного пункта — использовать самый консервативный известный отступ и явно помечать точку `norm_unverified` (никогда не имитировать точность, которой нет).
3. Буферы (`shapely.buffer`) вокруг каждой коммуникации на величину отступа; объединение с охранными зонами ЛЭП/ЗОУИТ/застройкой → единая запрещённая зона.
4. **Отдельно** — буфер вокруг каждого существующего насаждения с заключением `сохранить` (из перечетной ведомости, Этап 1 п.5) — источник ограничения здесь не норма, а конкретная запись ведомости (номер дерева/куста); добавляется в ту же запрещённую зону.
5. Допустимая зона = площадь участка минус запрещённая зона, с метаданными: какая часть какой конкретно нормой **или конкретным сохраняемым насаждением** ограничена.
6. Разбивка допустимой зоны по видам насаждений (дереву нужен больший отступ, чем кусту/траве — по каталогу посадок).

## Этап 3 — Генерация плана

Baseline — детерминированные правила/эвристики размещения точек в допустимой подзоне каждого типа (приоритет ТЗ — воспроизводимость и объяснимость важнее ML). Каждому объекту сразу присваивается заготовка обоснования из метаданных Этапа 2.

## Этап 4 — Агент ОТК (обязательный, независимый от генератора шаг)

Полное описание — [[ARCHITECTURE]] §3 и [[AGENTS_PLAN]] (агент 6). Кратко: генератор не является источником истины сам по себе — ни один результат не покидает пайплайн, пока агент ОТК не подтвердил:

1. **Сверку с картографической основой** — независимый пересчёт расстояний напрямую по исходной геометрии.
2. **Целостность слоёв** — исходные слои DXF не изменены.
3. **Консистентность ссылок на нормы** — каждое обоснование ссылается на верифицированную запись реестра; тексты обоснований собираются по шаблону из проверенных полей, не сочиняются свободно.
4. **Регрессию на эталонных данных** — сверка с «Пилотный проект 20 улиц» при наличии.

Результат ОТК — подтверждённый/отклонённый список + отдельный **Протокол технического контроля** (вердикт по каждой точке/зоне со ссылкой на то, какая проверка его дала).

## Этап 5 — Выдача ответа

1. **DXF-экспорт**: подтверждённые объекты — в выделенные слои (`GREEN_AI_*`), исходные слои копируются без изменений. Выполняется только после положительного протокола ОТК.
2. **Отчёт интерпретации**: JSON (основной) + человекочитаемый Markdown/HTML с визуальной план-схемой и таблицей обоснований (см. [[REPORT_DESIGN]]), плюс человекочитаемая часть протокола ОТК.
3. **(бонус)** Визуализация — только после успешного и подтверждённого ОТК DXF.
4. Результат + история прогона — в `data/processed/<id>/<версия_прогона>/`, без перезаписи предыдущих версий.

## Алгоритм добавления новой территории/схемы

1. Новая территория = новая папка в `data/raw/` с тем же контрактом входа, что в Этапе 0. Контракт — по типу файла и содержимому, не по точному имени папки (реальные 20 объектов уже показывают разнобой в названиях разделов, см. [[DATA_STRUCTURE]] §1).
2. Если формат подосновы отличается (DWG вместо DXF, другой набор имён слоёв) — Onboarding Agent сначала конвертирует (если DWG), затем пытается сматчить слои по расширяемому конфигу `data/reference/layer_name_aliases.yaml`; если не удалось — статус `manual_layer_mapping_required`, без тихого пропуска данных.
3. Если территория пересекается с новым видом ограничения, которого нет в реестре норм — статус `unclassified_constraint_zone`, зона исключается из допустимой площади консервативно, пока не классифицирована явно.
4. После успешной валидации и первого прогона территория переходит в реестр «обработанных», результат становится частью истории.

## История предыдущих посадок

- Каждый прогон версионируется (`data/processed/<id>/run_<timestamp>/`), ничего не перезаписывается.
- Реестр объектов хранит дату последнего прогона, статус, ссылку на последний подтверждённый план.
- Повторный запуск по известному объекту сравнивается с предыдущим подтверждённым планом (diff: новые коммуникации, новые ограничения, ручные правки) — отдельный отчёт, не просто перезапись.

## Геопривязка объектов — нужна ли она

**Да**, по трём причинам:
1. Отступы по 743-ПП/СП считаются в **метрах** — надёжно только при метрической CRS (например, МСК-77), а не в условных чертёжных единицах.
2. Кросс-референс с кадастром/открытыми геоданными/ЗОУИТ невозможен без общей системы координат.
3. «История посадок» и повторное использование данных по одному участку между прогонами имеют смысл только при идентификации по реальным координатам/кадастровому номеру, а не по имени файла.

Открытый вопрос — какая именно CRS используется в реальных DWG/DXF подосновах датасета (вероятно МСК-77) — см. [[OPEN_QUESTIONS]].
