# Структура данных — по результатам изучения реального датасета

Источник: `Датасет.zip` → `data/raw/dataset_extracted/` (локально, **не в git** — 23 ГБ, см. `.gitignore`). Состав архива:

```
Датасет/
├── Нормативные акты ссылки.docx        — список нормативных актов (см. docs/NORMATIVE_REFERENCES.md)
├── Шаблоны значков.dwg                  — библиотека блоков-значков для условных обозначений
└── Пилотный проект 20 улиц.zip          — 20 реальных объектов (папка на объект)
```

Это меняет и уточняет ряд допущений в [[ARCHITECTURE]]/[[DATA_ALGORITHM]] — ниже зафиксировано то, что реально наблюдается, а не то, что предполагалось до просмотра данных.

## 1. Структура одного объекта — реальная, не идеальная

20 объектов (папки `1. Олимпийская деревня`, `2. Песчаный переулок`, … `20. Макеева С. ул`). **Важно**: структура папок **не строго унифицирована** между объектами — разные названия одного и того же смыслового раздела («Исходные данные» / «ИСХОДНЫЕ ДАННЫЙ» / «Архивы», «Проектное решение» / «Проектные решения»). Это значит: Territory Onboarding Agent должен матчить по смыслу/эвристикам, а не по точному имени папки — жёсткий контракт «ровно такое-то имя папки» в реальности не выполняется.

Типовой (наиболее полный) состав объекта:

```
<N>. <Название улицы>/
├── Исходные данные/                              — то, что получено ДО проектирования
│   ├── <NNNNNN-2026_Название>/                    — регистрационный номер обращения (ИСОГД/госуслуга)
│   │   ├── 01 ирд/ (или "PaxHeader")               — ИРД: исходно-разрешительная документация
│   │   ├── <NNNNNNNN>_Генплан_<Название> - Standard/  — экспорт AutoCAD (eTransmit): DWG + Fonts + PlotCfgs + Textures
│   │   └── Дендрологические изыскания/             — результаты дендросъёмки от ГКУ «Дирекция Мосприроды» (не у всех объектов)
│   └── Архивы/ (иногда отдельно от "Исходные данные")  — те же материалы, упакованные в .zip
├── <Название> фото до/                            — фотофиксация участка (jpg/heic), десятки-сотни файлов на объект
├── Проектное решение/ (или "Проектные решения")   — ГОТОВЫЙ финальный проект — по сути эталонный выход для этого объекта
│   ├── DWG/                                        — финальные чертежи (посадочный, дендроплан) + eTransmit-бандл с текстурами/шрифтами
│   ├── PDF/                                        — те же чертежи в PDF + Excel-ведомости
│   ├── Раздел 1.1-ПЗ.pdf                           — пояснительная записка
│   ├── Раздел 1.2-ДО[_дата].pdf                    — «Дендрологическое обследование» (подраздел пояснительной записки)
│   ├── Раздел 2-АПОТ.pdf                           — проект организации работ
│   ├── Ассортимент <объект> <дата>.xlsx            — ведомость ПРОЕКТИРУЕМЫХ (новых) насаждений
│   ├── Перечетная ведомость_<дата>.xlsx/.pdf       — ведомость СУЩЕСТВУЮЩИХ насаждений (по дендрообследованию) + справочник пород
│   ├── Паспорт объекта / Пояснительная записка (.docx)
│   ├── ИнструкцияУход.docx                         — инструкция по уходу за посадками
│   └── <Название>_ракурс_N.jpg                     — рендеры/визуализации «после»
└── <Название>_ГП-NN.pdf                            — листы генплана
```

Не у каждого объекта есть все элементы (у части — только «Исходные данные» без готового проектного решения, у части — наоборот, готовый проект без явных исходных данных).

## 3. Критичное для архитектуры: DWG, а не DXF

ТЗ говорит о DXF на входе/выходе, но **весь реальный корпус проектных чертежей — в DWG** (собственный бинарный формат Autodesk), не в DXF. `ezdxf` (выбранная библиотека) **не читает бинарный DWG напрямую**.

Нужен явный этап конвертации перед Ingest: **DWG → DXF**. Стандартный отраслевой инструмент — **ODA File Converter** (Open Design Alliance, бесплатный, официальный) — имеет сборку под Linux (Debian/Ubuntu), что совместимо с целевой средой MosTex.OS. План:

1. На входе Service A принимаются оба варианта (DWG и DXF) — если пришёл DWG, перед `DXF Ingest Agent` выполняется автоматическая конвертация через ODA File Converter (headless/CLI-режим) в промежуточный DXF, который дальше идёт по обычному пайплайну.
2. Оригинальный DWG сохраняется как есть (наравне с «исходными слоями», неприкосновенен) — конвертированный DXF — это внутренний рабочий артефакт, не подменяющий источник.
3. Это отдельный явный шаг в `docs/CHECKLIST.md` и в Dockerfile (ODA File Converter должен быть в образе).

## 4. Два разных слоя ограничений по насаждениям — важное уточнение

До изучения датасета «карта ограничений» в [[ARCHITECTURE]] строилась только из инженерных коммуникаций/охранных зон. Реальный процесс показывает **второй, отдельный источник ограничений**:

- **Дендроплан + Перечетная ведомость существующих насаждений** — официальные результаты дендрологического обследования (для бюджетных объектов Москвы — от ГКУ «Дирекция Мосприроды»), с колонками: № (сохраняет исходную нумерацию, может прерываться), жизненная форма, порода, количество, диаметр (мин/макс), высота, характеристики состояния (1)(2)(3), **Заключение**: `сохранить` / `вырубить` / `пересадить` (обязательная колонка, заполняется заказчиком/дендрологом на основе колонки «рекомендации»).
- Деревья/кустарники с заключением `сохранить` — это **тоже запрещённая/ограничивающая зона** для новых посадок (нельзя посадить новое дерево там, где стоит сохраняемое старое, и физически нужен отступ от его кроны/корневой зоны), причём этот источник ограничений **независим** от инженерных коммуникаций и должен учитываться Constraint/Buffer Engine как отдельный тип зоны с собственным источником (не НПА, а конкретная запись перечетной ведомости).
- У той же ведомости есть встроенный **справочник пород с компенсационными коэффициентами** (см. §5) — это готовый, официальный видовой каталог, который частично закрывает потребность в Plant Catalog Agent (Фаза 2), но не даёт данных о глубине/росте корней — только жизненная форма, ценовой код и стоимость.

**Обновление для [[ARCHITECTURE]]/[[DATA_ALGORITHM]]**: Constraint/Buffer Engine получает на вход не только «коммуникации + ЗОУИТ + застройка», но и «существующие насаждения с заключением „сохранить“» — отдельный источник запрещённой зоны.

## 5. Официальный справочник пород — семя для Plant Catalog Agent

Лист «Справочник пород и текущая базовая стоимость зелёных насаждений для расчёта компенсационной стоимости и компенсационного озеленения» (внутри `Перечетная ведомость_*.xlsx`) содержит ~сотни видов с колонками:

`Идентификатор | Жизненная форма | Порода | Код ценности | Базовая компенсационная стоимость (без учёта коэф.), руб | Базовая компенсационная стоимость при компенсационном озеленении (без учёта коэф.), руб`

Сырой список строк выгружен в `data/reference/raw_species_directory_strings.txt` (1603 строки — сырой, требует структурирования по столбцам, следующий шаг). Это официальный, а не выдуманный источник видов — прямое основание для Plant Catalog Agent, но повторюсь: **глубины/прогноза роста корней там нет** — для этого по-прежнему нужен отдельный дендрологический источник (см. [[OPEN_QUESTIONS]]).

Также встречены явные признаки **инвазивных видов** («поросль инвазивных группы 2», «поросль инвазивных группы 3», «поросль малоценных пород») — прямая связь с найденным актом ППМ № 369-ПП (регулирование инвазивных растений, см. [[NORMATIVE_REFERENCES]]) — при проверке предлагаемых к посадке видов система должна сверяться с перечнем инвазивных видов из этого акта и не предлагать их.

## 6. Компенсационные коэффициенты вырубки (из «Памятка по дендроизысканиям.docx»)

Не относится напрямую к генерации НОВЫХ посадок, но важно как контекст (если проект предусматривает вырубку существующих насаждений под новые коммуникации/посадки, по регламенту считается компенсационная стоимость):

- Зона: 4,0 — внутри Садового кольца; 2,5 — от Садового кольца до МЦК; 1,0 — от МЦК до границ города.
- Близость к воде: 2,0 — в 50-метровой зоне от уреза воды; 1,0 — для остальных территорий.
- Коэффициент благоустройства — всегда 3,3.
- Тип объекта: 1,0 — городской заказ; 2,0 — прочие объекты.
- Базовый коэффициент — по памятке «10,13 на данный момент, обновляется каждый квартал» — то есть это внешняя, периодически обновляемая величина, её нельзя жёстко «зашивать» в код как константу.
- Коэффициент проектирования — всегда 1,05.

**Решение по объёму MVP**: этот расчёт — вне ядра ТЗ (задача — генерация новых посадок, не вырубка), фиксируется как кандидат для Фазы 2, если система расширится на сценарий «частичная вырубка существующих насаждений под новую посадку/коммуникацию».

## 9. Валидация вживую: DWG реально сконвертирован и открыт

Не гипотеза — реально сделано в этой сессии: скачан и установлен ODA File Converter, сконвертированы 2 реальных DWG в DXF, оба открыты и разобраны через `ezdxf`.

**Файл 1** — `Проектное решение/DWG/.../Разбивочно-посадочный.dwg` (итоговый посадочный план, Измайловская площадь): 429 слоёв, `INSUNITS=6` (метры). Реальная конвенция имён слоёв посадок:
- `DENDRO_TREE_<вид>`, `DENDRO_BUSH_<вид>` — один слой на вид растения, блоки (`INSERT`) считают количество экземпляров (напр. `DENDRO_BUSH_Пузыреплодник калинолистный 'Ред баронс'` × 378).
- `WOW_PLNT_TREES_<вид>`, `WOW_PLNT_BUSH_<вид>`, `WOW_PLNT_FLWRBED_<вид>`, `WOW_PLNT_LIANA_<вид>` — вторая, более детальная система слоёв для реалистичных 2D-блоков растений (библиотека блоков стороннего плагина «WOW»), с `WOW_LAND_*` для покрытий.
- `XREF_*` — внешние ссылки (подоснова подключена как xref, не влита в файл).
- `ACAD_TABLE` (12 шт.) — таблицы (ведомости) встроены прямо в чертёж, не только отдельным Excel.

**Файл 2** — `Исходные данные/.../_06_10000176_Генплан_Олимп.dwg` (топоплан + инженерные сети, объект «Олимпийская деревня»): 872 слоя, тоже `INSUNITS=6`. **Это и есть реальная геоподоснова с коммуникациями**, которую описывает ТЗ. Найдена чёткая, воспроизводимая конвенция имён (наследие формата обмена топографическими планами — суффиксы явно означают категорию):

| Суффикс источника | Смысл | Примеры найденных слоёв |
|---|---|---|
| `...up\|<слой>` | «Подземные коммуникации» | `Водопровод`, `Газопровод`, `Дренаж`, `Канализация напорная`, `Канализация самотёчная`, `Кабели`, `Кабель связи`, `Кабель электрический`, `Кабель защиты`, `Теплосеть`, `Трубопроводы`, `Общий коллектор`, `Промводопровод`, `Подземные коммуникации` (общий) |
| `...tp\|<слой>` | «Топоплан» | `Горизонтали`, `Геодезические пункты`, `Здания`, `Колодцы`, `ЛЭП`, `Опоры контактной сети`, `Отдельно стоящее дерево`, `Полоса деревьев`, `Ограды`, `Столбы`, `Указатель подз коммуникаций`, `Граница площадки/улицы`, `Береговая линия` |
| `...kl\|<слой>` | «Красные линии» | `Красные линии` (граница территории по градостроительной документации — самостоятельное планировочное ограничение, отдельное от кадастровой границы) |
| `...brd\|<слой>` | «Рамка листа» | `Граница заказа`, `Координатные кресты`, `Рамки`, `Подписи рамок` — служебные, не ограничение |

Плюс отдельный набор `_ГП_Колодцы Ремонт <ГАЗ/Канализ./Сети связи/Теплосеть/Водопр.>` — колодцы конкретно под ремонт, по виду сети.

**Вывод для словаря алиасов слоёв** (`data/reference/layer_name_aliases.yaml`, см. [[DATA_ALGORITHM]]): реальные слои — это не единый плоский список без структуры, а `<источник>|<название категории>`, где часть после `|` — это конечное, небольшое и предсказуемое множество русскоязычных названий (Водопровод/Газопровод/Кабель.../Теплосеть/ЛЭП/...). Матчинг по этой части (после `|`, без учёта префикса-источника) — рабочая стратегия для алиасов.

**Существующие деревья видны в ДВУХ разных представлениях**: как generic-точки на топоплане (`tp|Отдельно стоящее дерево`, `tp|Полоса деревьев` — без вида/номера) и как детальные блоки по видам в дендроплане/посадочном плане (`DENDRO_TREE_<вид>`). Constraint Engine должен уметь работать с обоими — на входной геооснове дерево может быть просто точкой без вида, вид и заключение «сохранить» приходят отдельно из перечетной ведомости (см. §4) и должны сопоставляться с этими точками по номеру/местоположению.

**Система координат — уточнение (важное расхождение с ранним предположением)**: единицы — метры (`INSUNITS=6`), но диапазон координат в тестовом файле (X: −2461…−368, Y: 260…1051) — это **не реальные геодезические координаты МСК-77** (там числа были бы порядка сотен тысяч), а **локальная/условная система координат конкретного чертежа**, завязанная на геодезические пункты и координатные кресты, отрисованные на самом чертеже (слои `Геодезические пункты`, `Координатные кресты`). То есть: отступы в метрах считать можно прямо в этой системе координат (единицы корректны), но **автоматической привязки к реальному месту на карте города через сами координаты DXF нет** — для кросс-референса с кадастром/открытыми геоданными нужен пересчёт через опорные геодезические точки (их подписанные координаты, если есть в тексте на чертеже) или через отдельно указанный адрес/кадастровый номер объекта. Обновляет предположение «вероятно МСК-77» в [[OPEN_QUESTIONS]]/[[DATA_ALGORITHM]] — само предположение о МСК-77 как целевой системе для координат опорных точек, вероятно, верно, но прямого доступа к ней через координаты геометрии в DXF нет.

## 10. Критичная поправка: главный «Генплан»-файл нельзя парсить напрямую — только компонентные файлы бандла

Найдено при реализации DXF Ingest Agent (2026-09-15), не на этапе первичного изучения — важное уточнение к §9.

Открыв и разобрав главный файл `_06_10000176_Генплан_Олимп.dwg` целиком, получил **0 объектов коммуникаций**, хотя в таблице слоёв документа они есть (872 слоя, см. §9). ## 11. Граница участка на реальных данных ненадёжна для автосборки — честно, не втихую

Слой `Граница площадки` в `tp.dwg` содержит 588 отдельных сущностей — при ближайшем рассмотрении это НЕ одна замкнутая полилиния, а россыпь отрезков. Прямая попытка найти замкнутый контур (LWPOLYLINE/POLYLINE closed) — 0 результатов. Добавлен fallback через `shapely.ops.polygonize()` (сборка полигонов из пересекающихся/стыкующихся отрезков) — технически сработал, но собрал полигон площадью 47 м² с bounding-box в разы меньше общего охвата всех 588 отрезков — то есть локально замкнул мелкий артефакт, а не реальный периметр участка.

**Решение**: `_find_site_boundary_in_doc()` считает `confidence` = отношение диагонали bbox найденного полигона к диагонали bbox ВСЕХ линий-кандидатов этого приоритетного слоя. Если `confidence < 0.5` — статус результата `found_low_confidence` (не `found`), геометрия всё равно возвращается (для ручной проверки), но automation (Constraint Engine) не должна тихо принимать её как надёжную. На объекте «Олимпийская деревня» реальный статус — именно `found_low_confidence`.

**Открытый вопрос на будущее**: для надёжного определения границы участка на реальных объектах, вероятно, потребуется либо (а) искать её не по линиям топоплана, а по кадастровым данным/ГПЗУ (внешний источник, не сам чертёж), либо (б) более сложная эвристика сшивки почти-смыкающихся отрезков с допуском по расстоянию (сейчас `polygonize` требует точного совпадения координат концов). Не решено, зафиксировано как ограничение MVP.

**Вывод, не реализовано в этом проходе**: `brd.dwg` — вероятно, наиболее надёжный (когда есть) источник границы участка, but не универсальное решение сам по себе (см. случай INSERT-блока выше). Два конкретных технических действия для следующего прохода:
1. Добавить `brd`-файл(ы) бандла в стандартный контракт входа Ingest (наравне с `up`/`tp`/`kl`) — искать по тому же принципу подбора «объект → компонентные DWG», не только `up`/`tp`.
2. Научить `_entity_to_geometry()`/`_find_site_boundary_in_doc()` резолвить `INSERT`-сущность на слое границы в реальную геометрию блока (через `entity.block()`/`virtual_entities()`, аналогично тому, как уже обрабатывались вложенные XREF в §10), а не отбрасывать её как точку.

Оба действия — НЕ выполнены, только диагностированы и подтверждены на конкретных примерах (не гипотеза). См. `docs/OPEN_QUESTIONS.md` — статус блокера демо обновлён.

### 11.3 (2026-09-15, тот же день) — найден и исправлен реальный баг выбора границы при объединении полного бандла; итог скорректирован

Пользователь задал простой проверочный вопрос («физически файлы открываются, данные достаются?») — в ответ на живую демонстрацию (полный Ingest реального объекта «Грузинская М ул» с выводом реальных координат и 85 411 объектов-ограничений) обнаружился регресс: при объединении `up`+`tp`+`brd` В ОДНОМ вызове (как реально работает `pipeline.run.py`) статус границы откатился на `found_low_confidence` (3,4 м²) — хотя изолированная проверка одного `brd.dwg` в §11.2 показала `found` (39 435 м²). **Причина — реальный баг в `ingest_dxf_files()`**: выбор границы среди кандидатов из разных файлов бандла сначала фильтровал по ЛУЧШЕМУ РАНГУ ИМЕНИ слоя (`site_boundary_layers`, порядок в `layer_name_aliases.yaml`) и только ПОТОМ, внутри этого ранга, сравнивал confidence. Если более приоритетный по имени слой (например «Граница площадки» в `tp.dwg`) давал мусорный низко-достоверный полигон через `polygonize()`, а менее приоритетный (например «Граница заказа» в `brd.dwg`) — надёжный явный замкнутый контур, движок молча выбирал МУСОРНЫЙ вариант только потому, что его слой был выше в списке приоритета. Приоритет имени перебивал достоверность геометрии — обратная логика тому, что нужно.
