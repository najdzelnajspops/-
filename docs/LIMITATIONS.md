# Ограничения, допущения, известные ошибки

Обязательный документ по ТЗ (`docs/TASK_BRIEF.md`, §6.8). Сводит воедино текущее (актуальное на дату документа) состояние — не историю расследования. Полный ход разбора каждого пункта, включая уже закрытые вопросы, — в `docs/OPEN_QUESTIONS.md` и `docs/SESSION_LOG.md`.

## Ограничения Constraint Engine (расчёта допустимых зон)

- **Отступ не зависит от вида/агрессивности корневой системы** — все деревья (и все кустарники) внутри своей жизненной формы получают одинаковый отступ от коммуникаций, хотя агрессивные виды (ива, тополь) на практике представляют больший риск для труб при том же формальном расстоянии. Источник данных по глубине/агрессивности корней конкретных видов не найден. Зафиксировано тестом (`tests/test_known_limitations.py`) как осознанное, а не случайное упрощение.
- **Отступ не учитывает диаметр кроны дерева свыше 5 м** — СП 42.13330.2016, Таблица 9.1 требует увеличения отступа для крупнокронных деревьев; каталог видов ДПиООС не содержит параметра диаметра кроны, поэтому норма не применяется.
- **Корнезащита при уменьшенном отступе** — норма, разрешающая уменьшенный отступ при условии инженерной корнезащиты, не найдена ни в 743-ПП, ни в СП 42.13330.2016. Не реализовано (не выдумываем номер пункта).
- **Дорожно-тропиночная сеть** — верифицированная норма отступа (743-ПП) есть в справочнике, но соответствующего слоя в реальных чертежах датасета обнаружить не удалось (ближайший слой «Бортовой камень» относится к границе проезжей части, другая норма).
- **Глубина коммуникаций не учитывается** — расчёт полностью 2D (по плану), профили/разрезы с реальной глубиной залегания сетей в контур Ingest не входят (в датасете таких документов нет).

## Ограничения по реальному датасету

- **9 из 20 объектов датасета полностью демо-готовы** (граница участка + коммуникации подтверждены); ещё несколько — граница есть, коммуникации не найдены. Остальные объекты требуют либо доп. слоёв границы (не найден нужный файл в eTransmit-бандле), либо явного архитектурного решения (например, «Кустанайская улица» — единственный кандидат на границу — слой «Красные линии», который по решению проекта не считается границей участка).
- **Реальная геопривязка (WGS84)** построена только для 2 объектов датасета («Олимпийская деревня» — надёжно, невязка ≤4,9 м; «Песчаный переулок» — метод признан ненадёжным и НЕ применён). Метод сопоставления по контурам зданий требует ориентировочно 10+ чётко различимых зданий на объекте — для малых/линейных участков не работает без другого источника опорных точек.
- **ЛЭП с неопределённым классом напряжения** получает самый широкий консервативный отступ (55 м, тариф 1150 кВ) — на одном реальном объекте это схлопнуло допустимую зону до 0,06% площади участка. Сервис явно показывает причину и число таких объектов в отчёте (`lep_unknown_voltage`), но сама причина (невозможность определить реальный класс напряжения по чертежу) не устранена — требует либо доп. источника данных, либо ручного ввода оператором.
- **Дендроплан существующих насаждений** учитывается только как «отдельно стоящее дерево»/«полоса деревьев» с консервативным буфером (6 м); сопоставление с конкретным видом из перечетной ведомости не реализовано.

## Реализовано, но с осознанными оговорками

- **Человекочитаемый отчёт** (2026-09-24) реализован в форматах Markdown + HTML (`pipeline/report/human_report.py`) — схема «до/после», таблица обоснований, протокол ОТК. **PDF сознательно не реализован** — по решению пользователя (2026-09-23): JSON+Markdown/HTML уже удовлетворяют ТЗ п.3.3 («на выбор команды»), а PDF потребовал бы новой тяжёлой зависимости (headless-браузер/weasyprint) с риском для воспроизводимости Docker-образа.
- **Условные обозначения по ГОСТ 21.508-2020** (2026-09-23) перенесены из ручного прототипа в реальный DXF-экспорт (`pipeline/export/dxf_export.py`) — дерево рисуется окружностью с крестом, кустарник — «пятном-массой» на группу с подписью числа экземпляров. Честный компромисс: `PlacementPoint` не хранит `cluster_id`, группировка кустарника для отрисовки — геометрическая кластеризация только на этапе экспорта, не в модели данных генератора. Из-за этого трассируемость id для дерева — 1:1 (как и раньше), а для кустарника — на уровне ГРУППЫ (подпись группы на чертеже ↔ координаты входящих в неё точек в JSON-отчёте), не отдельного экземпляра. Это соответствует самому ГОСТ 21.508-2020 (кустарник там тоже подписывается ведомостью по группе, не поточечно), но формально отличается от полной поточечной трассируемости, которая раньше была у ВСЕХ точек (включая кустарник) через `id`+`TEXT`.
- **Библиотека блоков-значков организаторов** («Шаблоны значков.dwg») (2026-09-24) частично интегрирована — по прямому указанию `docs/DATA_STRUCTURE.md`, §8 («подтягивать блоки из этого файла... а не рисовать свои произвольные значки»). Файл-источник оказался полноценным образцовым объектом организаторов (~130 определений блоков, в основном по конкретным видам растений), из которого извлечены и используются только 3 универсальных шаблонных блока по признаку хвойное/лиственное/кустарник: `Дерево_Л_С`, `Дерево_Х_С`, `Куст_Л_С` — вынесены в отдельный маленький `data/reference/planting_symbols.dxf` (72 КБ вместо 12 МБ полного образца). Реально используются только 2 из 3 (деревья `Дерево_Л_С`/`Дерево_Х_С` для ПРЕДЛОЖЕННЫХ точек, выбор по `chosen_species_entry.life_form_group_ru`) — блок кустарника `Куст_Л_С` НЕ используется: собственная отрисовка «пятном-массой» (`_draw_shrub_mass`) уже честно отражает реальную геометрию группы точек, что не хуже удовлетворяет тому же принципу «не рисовать произвольное», а организаторский блок кустарника рассчитан на одиночный экземпляр, а не на группу. Для ОТКЛОНЁННЫХ деревьев по-прежнему используется собственный примитив (круг с крестом) — для них вид/хвойность не выбираются (см. `pipeline/placement/generator.py`), значит подобрать нужный блок нечем. Внутренние сущности импортированного блока перепривязываются на слой `GREEN_AI_TREE_PROPOSED` (иначе агент ОТК 6.2 нашёл бы посторонние новые слои — `СП_дендроплан` и т.п., см. `pipeline/otk/layer_integrity.py`); подтверждено на реальном объекте «Песчаный переулок» (2026-09-24). ~130 видо-специфичных блоков организаторов (по конкретным породам вроде «Липа мелколистная», «Клен остролистный») НЕ интегрированы — потребовало бы надёжного сопоставления имени вида из каталога ДПиООС с конкретным блоком организаторов, чего исходный файл не гарантирует для всего каталога (сорта/синонимы, не все виды каталога вообще присутствуют среди блоков).
- **Выбор набора видов чек-боксами перед автогенерацией** (2026-09-24, прямой запрос пользователя, «список растений с чек-боксами, чтобы пользователь мог сначала задать перечень растений») реализован — `pipeline/placement/generator.py::pick_species_multi()`+`generate_placement(selected_species_names=...)`, чек-боксы с поиском на вкладке «Автоматическая генерация» веб-UI. Несколько выбранных видов распределяются по точкам round-robin (по кругу) в алфавитном порядке — детерминированно, без seed, тот же принцип воспроизводимости, что и везде в проекте; порядок ввода чек-боксов не имеет значения. **Известная оговорка, не исправленная в этом проходе**: `pipeline/export/dxf_export.py` при выборе блока-значка хвойное/лиственное (см. блоки организаторов выше) по-прежнему использует ОДИН представительный `chosen_species_entry` (первый элемент списка) для ВСЕХ предложенных точек дерева на участке, а не вид КОНКРЕТНОЙ точки — при многовидовом выборе с реально смешанными хвойными и лиственными видами это может дать неверный тип блока для части точек на итоговом DXF (сам JSON-отчёт и веб-UI показывают правильный вид каждой точки — ограничение касается только визуального значка в DXF-экспорте). Требует передачи `species_catalog` в `dxf_export.py` и поиска вида по `point.species_name_ru` для каждой точки отдельно — не сделано, т.к. чек-боксы делались для веб-UI, где DXF-экспорт не является основным сценарием использования этой вкладки.
- **Открытие итогового DXF в реальном CAD-приложении** (2026-09-24) подтверждено вживую: результат прогона на реальном объекте («Песчаный переулок») открыт в ZWCAD Viewer (AutoCAD-совместимый CAD-просмотрщик, установлен на машине разработки через winget — `ZWSOFT.ZWCADViewer`) — файл открылся без ошибок, схема (границы, блоки деревьев, слои) отобразилась корректно. При приближении к точкам посадки видно, что реально отрисован именно блок организаторов (`Дерево_Л_С`) — залитая зелёная крона с органичным неровным контуром (`HATCH`+`LWPOLYLINE`), не примитивная точка/окружность; рядом — id-метки (`tree_0001`, `tree_0003`, `tree_0004`) и подписи групп кустарника (`S-P001 (7 шт.)`, `S-P002 (7 шт.)`) — подтверждено скриншотом пользователя. **Оговорка**: это Windows-приложение ZWCAD Viewer, а не nanoCAD под MosTex.OS/Linux — целевая связка «MosTex.OS + nanoCAD» по-прежнему не проверена (нет доступа к реальной машине с этой ОС), но сама гипотеза риска — «а вдруг DXF вообще не откроется/повредится в стороннем CAD, `ezdxf` мог создать невалидный файл или блок сломается при вставке» — снята: файл читается настоящим CAD-приложением семейства AutoCAD, вставленный блок рендерится корректно, а не только программной библиотекой, которой он сам и создан.

## Осознанные инженерные допущения (явно не нормы, помечены `verified=False` в отчёте)

- **Отступ от существующих сохраняемых насаждений** — единой нормы нет, применяется практическая политика по категориям силы роста растения.
- **«Красные линии»** как зона запрета размещения — решение проекта, не прямая норма 743-ПП.
- **Размер группы кустарника** (7 шт. при кластеризации по норме густоты 623-ПП) — инженерное допущение, точного норматива размера группы не найдено.
- **Выбор вида среди равно допустимых** — алфавитный порядок как детерминированный тай-брейк (для воспроизводимости), источник не даёт критерия предпочесть один вид другому; явно объясняется пользователю (`TIE_BREAK_EXPLANATION`), не выдаётся за содержательное решение.
- **Размерный класс посадочного материала** («стандарт» vs «крупномер») при расчёте стоимости — по умолчанию «стандарт» для всех точек (Placement Generator не выбирает размер для конкретной точки).

## Известные технические особенности (не баги, задокументированное поведение)

- Реестр загруженных через веб-UI DWG/DXF-объектов живёт только в памяти процесса — не переживает перезапуск сервиса (осознанно, для живой презентации).
- Обработка загруженного через веб-UI чертежа — синхронная; для очень крупных объектов (десятки гектаров) может занимать несколько минут — интерфейс явно предупреждает об этом.
- Целенаправленное профилирование производительности не проводилось — текущее время прогона на крупном реальном объекте (~130 с) является побочным эффектом решения проблемы избыточной густоты кустарника, а не результатом отдельной оптимизации.
