# Дизайн отчёта по итогам прогона

Дополняет [[AGENTS_PLAN]] (агент №8, Interpretation Report Agent) и [[ARCHITECTURE]]. Отвечает на вопрос: что именно видит человек по итогам прогона, помимо текста.

(Документ изначально писался как общий для двух сервисов — Service A и вспомогательного Service B; последний по решению пользователя (2026-09-24) исключён из объёма проекта, см. `docs/OPEN_QUESTIONS.md`. Формулировки ниже уже приведены к одному сервису.)

## Принцип: один источник истины, несколько потребителей

DXF-слой результата, JSON-отчёт и визуальная схема в человекочитаемом отчёте строятся из **одного и того же** внутреннего geometry-объекта — списка объектов, уже прошедших агента ОТК. Рендерер схемы не рисует ничего "от себя" — он потребитель той же структуры данных, что и DXF Export Agent. Это гарантирует, что картинка в отчёте не может разойтись с тем, что реально лежит в DXF, и что в отчёте не может появиться ничего, чего не подтвердил ОТК.

## Формы вывода

| Форма | Аудитория | Формат |
|---|---|---|
| Машиночитаемый отчёт | интеграция, дальнейшая обработка, проверка 6.3 агента ОТК | JSON (основной), опц. CSV |
| DXF-слой результата | проектировщик в CAD | DXF, отдельный слой |
| Человекочитаемый отчёт | эксперт ДПиООС, жюри, оператор без CAD | Markdown/HTML, обязательно с визуалом (см. ниже) |

## Структура человекочитаемого отчёта

1. **Шапка**: объект/id территории, дата и версия прогона, версия реестра норм (`docs/NORMATIVE_REFERENCES.md`), использованные акты.
2. **Сводная таблица**: количество предложенных/отклонённых объектов по типам (дерево/куст/травяное покрытие), % соответствия нормам.
3. **Схема "до"**: план-вид участка + коммуникации (цвет по типу сети, в объёме, который реально известен) + существующие насаждения с заключением «сохранить» (отдельным условным обозначением — источник ограничения, не норма, а конкретная запись перечетной ведомости, см. [[DATA_STRUCTURE]] §4) + буферные зоны отступов (заливка: запрещено/допустимо/недостаточно данных), без слоя посадок.
4. **Схема "после"**: то же + слой результата — значки посадок с короткими id-метками (`T-014` и т.п.); отклонённые варианты — отдельным (серым) цветом.
5. **Таблица обоснований**: по каждому id/зоне — тип, координаты/контур, вердикт, норма-источник, пункт, фактическое расстояние до ближайшего ограничения. id совпадают с метками на схеме "после" — прямая трассируемость "посадка → норма → пункт", отдельно требуемая ТЗ.
6. **Протокол технического контроля (агент ОТК)** — человекочитаемая часть: по каждому пункту 6.1–6.4 ([[AGENTS_PLAN]]) статус проверки (пройдена/есть замечания) с итоговым числом подтверждённых/отклонённых/требующих ручной проверки объектов. Это отдельный, видимый пользователю раздел — не скрытая техническая деталь, а часть того, что доказывает отсутствие «чёрного ящика».
7. **Приложение**: отклонённые варианты с причиной отклонения и нормой, из-за которой отклонено.

## Технологии

- Рендер схемы: `matplotlib` (или самописный минимальный SVG-writer) поверх тех же `shapely`-геометрий, что идут в DXF-экспорт/GeoJSON-обработку. Без `geopandas` — лишняя тяжёлая зависимость, не нужна при уже выбранном шейповом стеке.
- Сборка PDF: связка Jinja2 → Markdown → PDF (см. `docs/reference_snippets/`), адаптированная под структуру выше.
- HTML-версия — тот же Markdown, отрендеренный в HTML, для живой проверки на демо.

## Осознанно не делаем (пока)

- **Интерактивная Leaflet/Mapbox-карта** — координаты подоснов, вероятнее всего, в локальной проекции (например МСК-77, метры), а не WGS84. Слипи-карта с тайловой подложкой требует репроекции, которая может быть избыточна для инженерной схемы участка. Возвращаемся к этой идее, если подтвердится, что данные геопривязаны в WGS84 (Фаза 2).
- **Фотореалистичная визуализация** — отдельный бонусный этап ТЗ (только Service A), генерируется только после подтверждённого агентом ОТК DXF; не заменяет и не смешивается со схемой "до/после" выше.
