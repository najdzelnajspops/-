# Назначение и границы решения

Обязательный документ по ТЗ (`docs/TASK_BRIEF.md`, §6.1). Сводит воедино то, что уже описано по частям в `docs/TASK_BRIEF.md`, `docs/ARCHITECTURE.md` и `docs/OPEN_QUESTIONS.md`.

## Назначение

Сервис принимает технический чертёж участка (DXF, либо DWG с автоматической конвертацией) с геоподосновой и слоями инженерных коммуникаций, вычисляет допустимые для посадки зоны с учётом нормативных отступов, и либо (а) сам предлагает план озеленения (деревья/кустарники, конкретные виды, количество), либо (б) проверяет план, предложенный человеком. Каждое решение — с обоснованием, ссылающимся на конкретный пункт нормативного акта. Результат выгружается обратно в DXF (отдельным слоем) и в машиночитаемый отчёт.

## Что входит в MVP (реализовано)

- **Service A — полный пайплайн по ТЗ**: DWG→DXF конвертация → DXF Ingest (разбор слоёв, границы участка, коммуникаций) → Constraint Engine (отступы 743-ПП/369-ПП/охранные зоны ЛЭП 160-ПП) → Placement Generator (автогенерация плана) → DXF Export (результат отдельным слоем) → Interpretation Report (JSON с обоснованием по каждой точке).
- **Placement Review Agent** — второй режим: человек сам предлагает вид и точку посадки, сервис независимо проверяет (каталог/инвазивность/фитосанитарная совместимость/отступы/густота) и честно объясняет нарушения, без автоматических исправлений.
- **Агент технического контроля (ОТК)** — независимая перепроверка отступов (6.1), целостности слоёв DXF (6.2), анти-галлюцинационная сверка обоснований (6.3), регрессия на эталонных данных (6.4).
- **CLI** — основной способ запуска по ТЗ (`pipeline.run`, `pipeline.review_run`).
- **Веб-UI** — второй способ запуска (плюс к ТЗ, не замена ядра): визуализация, оба режима, drag-and-drop, печать, загрузка своего DWG/DXF, обновление цен из прайс-листа питомника, панель нормативной базы, аудит-лог.
- **Docker-упаковка** — `Dockerfile`/`docker-compose.yml`, проверено внутри Linux-контейнера.
- **Swagger/OpenAPI** — из коробки на `/docs` (веб-UI построен на FastAPI).
- **Оценочная стоимость посадок** — по категориям (редактируемый человеком справочник цен), в обоих режимах.
- **Человекочитаемый отчёт (Markdown + HTML)** — схема «до/после», таблица обоснований, протокол ОТК (`pipeline/report/human_report.py`); PDF сознательно не реализован (см. `docs/LIMITATIONS.md`).
- **Условные обозначения по ГОСТ 21.508-2020 в реальном DXF-экспорте** — дерево (окружность с крестом), кустарник («пятно-масса» на группу).

## Что осознанно НЕ входит в MVP (оставлено на развитие)

- **Фотореалистичная визуализация** — явный бонус по ТЗ (§3.5), не блокирует сдачу ядра.
- **Карта + реестр зданий data.mos.ru** — сознательно отложено, отдельная задача.
- **Видо-специфичная агрессивность корневой системы / диаметр кроны дерева** — источник данных не найден, отступ одинаков для любого вида внутри категории «дерево»/«кустарник» (см. `docs/LIMITATIONS.md`).
- **Полный Plant Catalog с прогнозом роста корней, история прогонов, оверлей загруженного плана** — продуктовая надстройка Фазы 5, вне контура хакатона.

**Исключено из объёма проекта (не «на развитие», а окончательно отменено)**: Service B — второй сервис «разовая рекомендация» по PDF/Excel/DOCX без полноценной геоосновы, ранее спроектированный в `docs/ARCHITECTURE.md` §0. Не требовался по ТЗ (`docs/TASK_BRIEF.md` описывает только вход Service A), кода не было написано ни строки. По решению пользователя (2026-09-24) исключён из объёма проекта окончательно — см. `docs/OPEN_QUESTIONS.md`. Вместе с ним снят и вопрос OCR сканированных PDF (был актуален только для этого сервиса).

## Целевая среда

Продукт ориентирован на **MosTex.OS** (Linux-дистрибутив экосистемы МосТех) как целевую ОС заказчика; разработка велась на Windows с проверкой в Docker/Linux-контейнере и WSL. Упаковка — Docker (Kubernetes не обязателен по ТЗ).
