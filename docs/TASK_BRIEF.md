# ТЗ — сжатая выжимка (источник: docs/tz_source/03_dpioos_tz.pdf)

Кейс хакатона: «Проект Мэра Москвы» / «Бизнес Москвы» / «Лидеры цифровой трансформации» / «Контроль Москвы. Экология». Заказчик — ДПиООС (Департамент природопользования и охраны окружающей среды города Москвы). Год: 2026.

## 1. Суть задачи

Построить алгоритм / ИИ-модель (сервис или скриптовый пайплайн), который:

- принимает на вход **DXF** (геоподоснова + слои инженерных коммуникаций) и связанные данные;
- считает **допустимые зоны/точки посадки** зелёных насаждений с учётом нормативных отступов от подземных коммуникаций и охранных зон;
- **генерирует план посадки** (деревья, кустарники, травяные покрытия, элементы скверов);
- отдаёт результат **обратно в DXF**, но только на отдельном(-ых) слое(-ях) — исходные слои подосновы/коммуникаций/городской среды не меняются и не перезаписываются;
- для **каждой** предложенной (и отклонённой) посадки формирует **объяснение со ссылкой на конкретный НПА и пункт** — это обязательное требование к качеству результата, «чёрный ящик» без ссылок на нормы не принимается как полноценное решение.

Приоритеты по ТЗ (дословно): 1) рабочий алгоритм/пайплайн DXF→обработка→DXF — главное; 2) UX/UI — второстепенно, достаточно CLI/минимальной формы; 3) способ «мозга» на выбор команды — правила/буферы/эвристики, ML/generative AI или гибрид, но результат обязан быть **корректным, воспроизводимым и объяснимым**.

## 2. Что сервис должен уметь (входы/анализ/выход)

**Вход:**
- геоподосновы («Геотрест» и аналоги — DWG/SHP/GeoJSON);
- данные публичных кадастров;
- слои инженерных коммуникаций;
- функциональное зонирование и элементы городской среды (улицы, здания, транспортная инфраструктура).

**Анализ ограничений → карта «где можно сажать»:**
- нормативные отступы от подземных сетей (кабели, водопроводы, газопроводы и др.);
- охранные зоны ЛЭП и иные зоны охраны;
- плотность застройки, существующая инфраструктура, климатические и типовые условия посадки (по доступным справочникам).

**Рекомендация локаций** для типовых посадок: деревья, кустарники, травянистые покрытия, элементы скверов и иных типовых решений.

**Генерация плана** посадки деревьев/кустарников с соблюдением норм и параметров тестового участка.

## 3. Жёсткие требования к результату

1. **Слои**: весь сгенерированный результат — только на отдельном слое/слоях чертежа (например `PLANTING_PROPOSED`, `GREEN_AI`); можно несколько dedicated-слоёв по типу посадки (деревья/кустарники/покрытия), но без смешивания с исходной геометрией.
2. **Экспорт** — обратно в DXF, открываемый в CAD целевой среды (nanoCAD и иные Linux/MosTex.OS-совместимые средства просмотра/редактирования).
3. **Интерпретируемость** — обязательна для каждой точки/объекта посадки:
   - объяснение почему здесь можно/нужно сажать именно этот тип насаждения;
   - обязательная ссылка на нормативный акт и конкретный пункт/таблицу/норму отступа (СП 42.13330.2016 — п. …; 743-ПП — п. …; 623-ПП/требования МГСН — п. …);
   - если посадка запрещена/отклонена алгоритмом рядом с коммуникациями/охранными зонами — тоже фиксируется причина со ссылкой на норму;
   - объяснения выгружаются отдельно (JSON/CSV/Markdown/PDF на выбор команды) и/или как атрибуты/текстовые пометки на слое результата.
4. **Коррекция результата** (желательно, не блокирует) — параметрами/конфигом/правками списка посадок; при наличии UI — переносом точек на схеме. Минимально допустимо на хакатоне: перезапуск пайплайна с изменёнными параметрами.
5. **(Бонус, не блокирует сдачу ядра)** — после финального DXF сгенерировать фотореалистичные визуализации участка «как будет выглядеть после озеленения», согласованные с планом посадок.

## 4. Нормативные ориентиры (цитировать точно, не изобретать пункты)

- СП 42.13330.2016 — градостроительные нормы планировки и застройки.
- Постановление Правительства Москвы № 743-ПП — в т.ч. отступы от трубопроводов (в ТЗ упомянут пример: не менее 2 метров — **это пример из ТЗ, не полный список**, точные пункты нужно сверять по первоисточнику).
- Постановление Правительства Москвы № 623-ПП и требования МГСН (Мосгосстройнадзора) — дополнительные городские требования к размещению насаждений и их согласованию.

> См. [[NORMATIVE_REFERENCES]] — реестр норм, куда заносим точные пункты только после верификации по первоисточнику. Правило проекта: без верифицированного пункта — статус «[требует верификации]», не гадать.

## 5. Программно-аппаратные требования (критично для архитектуры)

- **Целевая ОС продукта — MosTex.OS** (Linux-дистрибутив экосистемы МосТех города Москвы, по среде исполнения близок к Ubuntu). **Windows не является целевой ОС** для контура заказчика — только для локальной разработки допустим совместимый Linux.
- Обязательна упаковка в **Docker** (Dockerfile и/или docker-compose); Kubernetes — по усмотрению, не обязателен.
- Если есть HTTP API (бэкенд) — обязателен **OpenAPI/Swagger**.
- Стек языков/библиотек не регламентирован.
- Ориентир по мощности рабочей станции (для тяжёлых DXF): CPU ≥3 ГГц/8 ядер, RAM 16–32 ГБ, GPU 4–8 ГБ VRAM, SSD от 512 ГБ — это ориентир для CAD-совместимости, не жёсткое требование к самому пайплайну.

## 6. Обязательная документация (без неё решение не считается сданным)

1. Назначение и границы решения — что в MVP, что оставлено на развитие.
2. Архитектура (компоненты, потоки данных, схема развёртывания Docker/K8s).
3. Описание работы алгоритма/ИИ-модели — обязательно: текстовое пояснение логики (отступы, типы посадок, приоритеты, работа со слоями DXF), описание механизма интерпретируемости, **схема процесса — предпочтительно BPMN** (или UML Activity/flowchart/data-flow), от входного DXF до выходного (и до визуализаций, если бонус).
4. Используемые методы и библиотеки (со ссылками на источники/модели).
5. Инструкция по сборке/запуску/проверке (пошагово: Docker-команды, как прогнать DXF и получить результат на MosTex.OS).
6. Способ взаимодействия (CLI/скрипт/UI).
7. Swagger/OpenAPI, если есть бэкенд/HTTP API.
8. Ограничения, допущения, известные ошибки.

## 7. Ресурсы, которые предоставляют организаторы

- Примеры чертежей (DXF) с размеченными коммуникациями.
- Наборы параметров для тестовых участков озеленения.
- Обезличенные подосновы АО «Мосгеотрест» (DWG/SHP/GeoJSON — по наличию).
- Открытые геоданные Москвы (data.mos.ru): улицы, здания, границы участков, транспортная инфраструктура.
- Каталоги типовых посадок с нормами по отступам и условиям посадки.
- Справочные данные по инженерным сетям, зонам охраны, охранным зонам ЛЭП.
- Пространственная основа для визуализации (Leaflet, Mapbox и др.).
- Датасет **«Пилотный проект 20 улиц»**: входные данные по папкам объектов (геоподоснова+коммуникации+файлы для входа пайплайна на объект), эталонные выходы — отдельными файлами без вложенных папок на верхнем уровне (для сопоставления вход→ожидаемый выход). Доступ — «в личном кабинете кейса» (см. [[OPEN_QUESTIONS]] — нужно уточнить доступ).

## 8. Сдача решения

- **Промежуточный этап**: приём тестового DXF, расчёт зон по базовым отступам, генерация первичного плана хотя бы для одного типа насаждений, результат на отдельном слое, черновик интерпретируемости (частичный охват), краткое описание логики, живая демонстрация на ноутбуке (CLI допустим). Полноценный UI не требуется.
- **Финал**: полный импорт/разбор DXF+геоданных по тестовым участкам (в т.ч. «Пилотный проект 20 улиц»), рекомендации локаций для нескольких типов посадок, автогенерация плана с отступами, результат только на отдельном слое, экспорт в DXF, полный интерпретируемый отчёт (JSON/CSV/Markdown/PDF), способ параметризации/повторного прогона, документация (текст+BPMN), Swagger (если бэкенд), презентация (10–20 слайдов, pptx/pdf), материалы: репозиторий, презентация, способ запуска (Docker), документация, файл(ы) интерпретации.
- Демо: 4–10 минут, живой прогон, обязательно показать вход DXF → работу алгоритма → выходной DXF на отдельном слое → пример интерпретации со ссылкой на НПА → проверку в CAD-просмотрщике под MosTex.OS/Linux.

## 9. Критерии оценки (сжато)

Ценность идеи и оригинальность подхода; прозрачность логики отступов и работы со слоями; **качество интерпретируемости (ссылки на НПА и пункты по каждой посадке)** — явно выделено как отдельный критерий; воспроизводимость пайплайна DXF→результат→DXF; устойчивость парсинга; скорость; трассируемость «посадка → норма → пункт»; инфраструктурная подъёмность (Docker/K8s); Swagger при бэкенде; UI — плюс, не замена ядра; практическая применимость точек посадки; проверяемость обоснований; полнота результата для передачи в CAD.

## 10. Возможности после конкурса

Полное выполнение ТЗ → пилотное тестирование с перспективой внедрения. Частичное выполнение → консультационная поддержка на доработку. Варианты внедрения → пилотирование ИТ-решения на ресурсах ДПиООС, трудоустройство участников в подведомственные учреждения.
