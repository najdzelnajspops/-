# Тестирование — как это устроено на самом деле

Написано по прямому вопросу пользователя (2026-09-15): «как ты проводишь тесты, кто следит за этим, как ты понимаешь, что тест пройден» — до этого момента процесс жил только в голове у Claude, не в проекте. Здесь — без приукрашивания, включая то, чего НЕТ.

## Как запустить

```
cd "D:\Загрузки\Проекты\Проект озеленения территории"
python -m pytest tests/ -q      # коротко: только итог
python -m pytest tests/ -v      # подробно: имя каждого теста + PASSED/FAILED
```

Два медленных теста прогоняют реальные объекты датасета и автоматически пропускаются (`SKIPPED`), если распакованного датасета и/или ODA File Converter нет на диске (`data/raw/dataset_extracted/`, вне git) — не ломают прогон на машине без датасета:
- `test_dwg_convert.py::test_convert_dwg_to_dxf_end_to_end_on_real_object` — реальный объект на 140k+ сущностей.
- `test_service_a_regression.py::test_real_object_matches_golden_baseline_and_is_reproducible` (2026-09-17, агент ОТК 6.4) — полный прогон Service A 5 раз подряд на реальном объекте, ~1 минута.

## Что значит «тест прошёл» — буквально

`pytest` собирает все функции `def test_*` в `tests/`. Внутри каждой — обычные `assert`. Если функция выполнилась до конца без необработанного исключения — `PASSED`. Если какой-то `assert` оказался `False` — `pytest` ловит `AssertionError`, печатает точное место и значения (не просто «упало»), помечает `FAILED`. Итоговая строка (`13 passed`, `1 failed`) и код возврата процесса (`0` — всё прошло, не `0` — что-то упало) — это и есть источник истины. Никакого субъективного «на глаз похоже на правду».

## Кто следит за тестами — честно

**Никто автоматически.** Нет CI, нет агента, который бы сам запускал тесты после изменений или анализировал, насколько они точны/полны. Запускаю их я (Claude) вручную через Bash после значимых изменений, читаю вывод, реагирую на FAILED. Это значит:

- Если я забуду прогнать тесты после правки — ничто не поймает это автоматически.
- Если сам тест написан неточно (проверяет не то, что нужно, или недостаточно строго) — pytest этого не заметит, он проверяет только то, что явно записано в `assert`. Пример из этой же сессии: синтетические тесты `test_buffer_engine.py` не поймали бы проблему «отступ не зависит от агрессивности корневой системы куста» — потому что такой assert никто не писал, пока пользователь не спросил прямо.
- Единственный механизм, частично компенсирующий это — прогон на РЕАЛЬНЫХ данных (`test_convert_dwg_to_dxf_end_to_end_on_real_object`), который уже дважды в этой сессии ловил баги, которые синтетика пропустила (см. `docs/SESSION_LOG.md`, находки про XREF-бандл и про группировку границы участка).
- Агент ОТК (см. `docs/AGENTS_PLAN.md`) проверяет ВЫХОД конкретного прогона на реальном объекте (регрессия на эталонных данных, п.6.4, реализовано 2026-09-17 — `test_service_a_regression.py`) — это не то же самое, что проверка качества тестового набора, но частично играет ту же защитную роль для продакшн-результата. Этот же тест на первом прогоне поймал реальную находку (не логическую регрессию, а ezdxf-метаданные момента сохранения — см. `docs/SESSION_LOG.md`, 2026-09-17) — иллюстрация того, что реальные данные ловят то, что синтетика не увидит.

## Что реально покрыто тестами (на 2026-09-15)

| Компонент | Покрыт | Как |
|---|---|---|
| Offset Registry (743-ПП) | Да | Загрузка YAML, конкретные значения по видам сети |
| Buffer Engine | Да | Синтетика + адверсарная геометрия (25 повторов, 40 пересекающихся буферов) |
| Охранные зоны ЛЭП (160-ПП) | Да | По классам напряжения, включая явную ошибку при неизвестном классе |
| Инвазивные виды (369-ПП) | Да | По ру/лат названию |
| Повторяемость (одна платформа) | Да | Два независимых прогона, `shapely.equals`, идентичный порядок отчёта |
| Повторяемость (кросс-платформенно) | Да | Windows ↔ WSL Ubuntu 26.04, побайтовое сравнение вывода |
| DXF Ingest | Да | Синтетический DXF + реальный объект (140k+ сущностей) |
| DWG→DXF конвертация | Да (если ODA File Converter установлен) | Реальный DWG-бандл |

## Что НЕ покрыто — явно, не по умолчанию

- **Видо-специфичная логика отступов** (агрессивность корневой системы) — не реализована и, соответственно, не тестируется. См. `docs/OPEN_QUESTIONS.md`.
- **Placement Generator** — не существует, нечего тестировать.
- **Агент ОТК** — не реализован (кроме концептуально пересекающихся проверок, уже встроенных в buffer_engine/dxf_ingest — например, `verified=False` пометка).
- **Внутри самого Docker-образа** — повторяемость проверена на WSL Ubuntu, не в контейнере (Dockerfile ещё не написан).
- **Качество/полнота самого набора тестов** — не проверяется ничем, кроме ревью пользователя и здравого смысла автора тестов (см. раздел выше).
